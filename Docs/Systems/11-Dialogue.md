**References:** Epic has no dialogue system. Epic's "String Tables" and "Localization" pages (stable keys, CSV import, `FText::FromStringTable`, `UKismetTextLibrary::TextFromStringTable`), "Data Assets" and "Asset Management" (primary asset types), and the `EditInlineNew` / `Instanced` specifiers for objects inside an asset (as our item fragments use, [section 8](08-Inventory.md)). Lyra has no dialogue; its `ULyraInventoryItemFragment` pattern (small instanced objects selected in data) is the model for conditions and outcomes.

**Rules:**

- **Dialogue is data**, never C++ or Blueprint graphs per conversation. Conditions and outcomes are small, named, data-selected types (instanced objects), and a mod adds a conversation by adding a data asset, and a new kind of condition by a Blueprint subclass.
- **Relationship state** (met, earned trust, flags, later seen lines) lives in one owner, `UVestigeRelationshipComponent` on the player state, keyed by the character's `FPrimaryAssetId`. Robots don't store how the player feels about them.
- **Running a talk** is `UVestigeConversationComponent`'s, on the player state: choosing the conversation, the current line, the choices, applying outcomes, holding the clock. The box is presentation: it shows what the component says and reports presses.
- Saves store character IDs and their state, never line text or positions in a list.
- Every line is `FText` from a string table, keyed by the writer's stable line ID ([section 18](18-Localization.md)).

**The data** (all in `Content/`, so conditions and outcomes can be referenced by any content):

- **`UVestigeDialogueData`**, a `UVestigeContentData` of primary asset type `VestigeDialogue` (scanned in `Content/Vestige/Dialogue`, always cooked; the catalogue loads it with the rest of the content, text only). One asset per conversation: `DA_Dialogue_HobFirstMeeting` (`Base.HobFirstMeeting`), `DA_Dialogue_HobGreetingMorning`, `...Afternoon`, `...Evening`, `...Late` and `DA_Dialogue_HobAgainToday`. Fields:
   - `Speaker`: `FPrimaryAssetId`, `AllowedTypes = "VestigeCharacter"`, checked with `FindContentReferenceError`. The conversation names its character, not the other way round, so a mod adds a conversation to Hob without editing Hob's asset (content is discovered, [Architecture.md, section 12](../Architecture.md#12-designing-for-mods)).
   - `Priority` (`int32`): among the speaker's conversations whose conditions all hold, the highest wins. Hob's: first meeting 100, the four greetings 50, again today 10.
   - `Conditions`: `TArray<TObjectPtr<UVestigeDialogueCondition>>`, `Instanced`. All must hold.
   - `Lines`: `TArray<FVestigeDialogueLine>`, played from the first.
- **`FVestigeDialogueLine`**: `LineId` (`FName`, the writer's ID, `Hob.Meet.010`; for a pool, the pool's ID, `Hob.Greet.Morning`), `Texts` (`TArray<FText>`, usually one; several make a pool, below), `Next` (`FName`: the line that follows; `None` means the next line in the array, the last line ends the talk, and `VestigeDialogue::EndTalk`, "End", ends it after this line, which a line in the middle of the array needs, such as a reply's answer), `Choices` (`TArray<FVestigeDialogueChoice>`; at most `VestigeDialogue::MaxChoices`, 3, are listed at once, below), `Outcomes` (instanced `UVestigeDialogueOutcome`s, applied when the line is shown).
- **`FVestigeDialogueChoice`**: `ReplyId` (`FName`, `Hob.Meet.Reply.Thanks`), `Text`, `Next` (required; a line's ID or `EndTalk`), `Conditions` (a choice whose conditions fail isn't listed), `Outcomes` (applied when chosen). A line with choices shows its text and then its choices under it, the line still showing; nothing advances until one is chosen.
- **Pools.** A line with several `Texts` shows one: index `(Day + TalksTodayBefore) % Texts.Num()`, where `TalksTodayBefore` is how many talks with this character came before this one today. It is stateless and testable, and gives what the writer asks: the day's first talk (the greeting, `TalksTodayBefore` 0) never repeats yesterday's, since consecutive days differ by one, and later talks (again today) never repeat the one before. A reload can repeat a line; harmless (the writer's note).
- **Conditions: `UVestigeDialogueCondition`** (`Abstract`, `Blueprintable`, `EditInlineNew`, `DefaultToInstanced`), with `UFUNCTION(BlueprintNativeEvent) bool IsMet(const FVestigeDialogueContext& Context) const`, an extension point. It must be cheap and change nothing. A condition is an object inside a data asset, so it has no world of its own: a Blueprint condition can't call nodes that need a world context, and reads what it needs from the context (its `Player`'s components, through their getters). A world for Blueprint conditions and outcomes (`GetWorld` returning the context player's while they run) is added when the first one needs it. Built now:
   - `UVestigeDialogueCondition_HasMet` (`bMet`, default true): the player has met the speaker.
   - `UVestigeDialogueCondition_TalkedToday` (`bTalked`, default true): a talk with the speaker already started today.
   - `UVestigeDialogueCondition_TimeOfDay` (`FromHour`, `ToHour`, in the clock's `GetTimeOfDay` hours, so after midnight is 24 to 30): `FromHour <= TimeOfDay < ToHour`. The bands are the writer's assumption until the game designer sets them: 6 to 12, 12 to 18, 18 to 24, 24 to 30.
   - `UVestigeDialogueCondition_Trust` (`MinTrust`, `int32`, at least 0): `Context.Trust >= MinTrust`. A step's threshold lives in its step talk's condition, the one place it is used.
   - `UVestigeDialogueCondition_Flag` (`Flag`, a gameplay tag; `bSet`, default true; `MinDaysSince`, default 0; `MaxDaysSince`, default -1 for no limit): the flag counts as set when the context has it and `Context.Day - its day` is within `MinDaysSince` to `MaxDaysSince`; the condition holds when that equals `bSet`. So "set, at least a day ago" is `bSet`, `MinDaysSince` 1; "set today" is `bSet`, `MaxDaysSince` 0; "not set in the last two days" is `bSet` false, `MaxDaysSince` 1.
   - `UVestigeDialogueCondition_Milestone` (`Milestone`, a gameplay tag; `bReached`, default true): whether the context's milestones have it.
   - `UVestigeDialogueCondition_Date` (`FromDay`, the game's day count, default 1; `Season`, a tag under `Vestige.Season`, empty for any; `FromDayOfSeason`, default 1; `ToDayOfSeason`, default 0 for the season's last): `Day >= FromDay`, the season matches when one is named, and `FromDayOfSeason <= DayOfSeason` and, unless 0, `DayOfSeason <= ToDayOfSeason`. A topic's "from day 2" is `FromDay` 2 (a reload on day 1 forgets the day's talks, so "not talked today" alone could offer a topic on day 1); SeasonEnd is `Season` Spring, 19 to 25.
- **`FVestigeDialogueContext`** (`BlueprintType`), filled by the conversation component before choosing: `Speaker` (the character data), `Player` (`APlayerState*`, for a mod's condition that needs more), `Day`, `TimeOfDay`, `bHasMet`, `TalksToday` (the context that chooses the conversation is made before the talk is recorded, so it has the state before this talk; the contexts of its lines, replies and outcomes are made after, so they count this talk and `bHasMet` is true), `Trust` (`int32`, the relationship component's `GetTrust`: earned points plus the speaker's points for milestones reached), `FlagDays` (`TMap<FGameplayTag, int32>`, a copy of the speaker's flags with the day each was last set) `Milestones` (`FGameplayTagContainer`, a copy of the milestones reached), and `Season` and `DayOfSeason` (from the clock's `GetDate()`). Our conditions read only its values, so they are pure and need no world in tests. The copies are a few entries each, made once per line shown.
- **Outcomes: `UVestigeDialogueOutcome`** (`Abstract`, `Blueprintable`, `EditInlineNew`, `DefaultToInstanced`), with `UFUNCTION(BlueprintNativeEvent) void Apply(const FVestigeDialogueContext& Context) const`, an extension point. Outcomes change state only through their owners' functions. The base is in `Content/`; an outcome that asks an owner in a higher layer lives in that layer, as the two built ones do (`Characters/`, beside the relationship component, which `Content/` may not include; an asset names its outcome's class by path, so the folder doesn't matter to the data):
   - `UVestigeDialogueOutcome_AddTrust` (`Amount`, `int32`, at least 1): `UVestigeRelationshipComponent::Find(Context.Player)->AddTrust(Context.Speaker, Amount)`.
   - `UVestigeDialogueOutcome_SetFlag` (`Flag`, a gameplay tag): `SetFlag(Context.Speaker, Flag, Context.Day)`; setting it again moves its day to today.
   - Without a context player or a relationship component they do nothing (a test's bare context).
- **At most 3 replies are listed.** `EnterLine` lists the choices whose conditions hold, in order, and stops at `MaxChoices`; when more hold, it logs a `Warning` (`LogVestigeDialogue`, the conversation's and the line's IDs) and the rest are left out, so the listed replies and the box's buttons always match. More holding at once is a data mistake.
- **Validation** (`UVestigeDialogueData::IsDataValid`): a known speaker; at least one line; unique `LineId`s and `ReplyId`s, and no `LineId` of "End" (`EndTalk` is reserved for ending the talk); every `Next` names a line of this asset or is `EndTalk`; every line has at least one text; at most 3 choices without conditions (a line may hold more entries when the ones beyond carry conditions, such as a reply entered twice for two steps; whether two conditional replies can hold together is the data's to keep apart, and the run-time cap below catches it); every text, line or reply, comes from a string table (`FTextInspector::GetTableIdAndKey`), else a warning; no null condition or outcome; and each condition's and outcome's own `IsDataValid` (`WITH_EDITOR`), which the dialogue asset calls: a flag or milestone condition, and a `SetFlag`, need a valid tag; `MinDaysSince` at least 0 and `MaxDaysSince` -1 or at least `MinDaysSince`; `AddTrust`'s `Amount` at least 1; `MinTrust` at least 0.
- **Flags and milestones are gameplay tags** in `Config/DefaultGameplayTags.ini`, content-only (no C++ names them): flags under `Vestige.Relationship` (`Vestige.Relationship.Step.Attentive`, `.Step.WouldLike`, `.Step.Memory`, `.Step.WouldLikeOffered`, `.Asked`, `.Help.Watering`, `.Helped.Watering`, `.WateredMentioned`, `.TopicOffered`, `.Topic.<Name>`), stored per character, so one flag tag serves every character; milestones under `Vestige.Milestone` are native ("The farm's firsts", below). The properties carry no `Categories` filter, so a mod's own root can be picked; validation catches a missing tag.

**The text.** Lines are entries of one string table, `ST_Dialogue` (`Content/Vestige/Dialogue`), whose key is the writer's ID (`Hob.Meet.010`, `Hob.Greet.Morning.1`, `Hob.Meet.Reply.Name`), and each `FText` in the data is linked to its entry. Why: the keys are stable and readable, the writer's IDs are already that, translators get one table, and a script that makes the assets can link text with `UKismetTextLibrary::TextFromStringTable` (text set from a plain string in a script is culture-invariant and never gathered for translation, which is how `WBP_Hud`'s preview texts turned out, [section 6](06-UserInterface.md)). The table is filled from the writer's Ready file ([Spoilers/Dialogue/Hob-Everyday.md](../Spoilers/Dialogue/Hob-Everyday.md)); a mod ships its own table. The speaker's name is the character's `DisplayName`; reply lines have no speaker. Limits: a line at most 150 characters, a reply at most 40 (English), checked by a test over every dialogue asset, so the box never overflows.

**The characters' data: `UVestigeCharacterData`** (`Content/`), a `UVestigeContentData` of primary asset type `VestigeCharacter` (scanned in `Content/Vestige/Characters`, always cooked), for robots and humans alike: `DA_Character_Hob`, `Base.Hob`, display name "Hob". Its own fields now: `CharacterTags` (`FGameplayTagContainer`, `Categories = "Vestige.Character"`; `Vestige.Character.Robot` or `Vestige.Character.Human`, tags in `DefaultGameplayTags.ini` since no C++ reads them) and `TrustFromMilestones` (`TMap<FGameplayTag, int32>`, `EditDefaultsOnly`: the trust points each milestone gives toward this character; validation: valid tags, points at least 1; Hob's: `Vestige.Milestone.Farm.Harvested`, `.Sold` and `.Cleaned`, 1 each). The schedule and the body class to spawn are added when their items come ([section 10](10-Robots.md)). A character's conversations aren't listed on it (above).

**Running a talk: `UVestigeConversationComponent`** (`Characters/`, a component on `BP_PlayerState`, added in `AVestigePlayerState`'s constructor like the rest component). Found with `static Find(const AActor* PlayerActor)` (a pawn or the player state, as `UVestigeRestComponent::Find`). Not saved: a talk never spans a save point.

- **`bool StartConversation(AActor& SpeakerActor, const UVestigeCharacterData& Speaker)`**, asked by the speaker's `Interact`. Refuses (returns false, changes nothing) while a talk runs, and while the player's ability system has `Vestige.State.UsingTool` (a use in progress or E held: a use mustn't finish behind the box, and the talk shouldn't depend on Common UI's flush of pressed keys, `CommonUI.AutoFlushPressedKeys`, to release E). Otherwise it fills the context, finds the speaker's conversations in the catalogue (`UVestigeContentCatalog::FindAll(VestigeDialogue)`, a loop over the few dialogue assets, once per talk), keeps those whose `Speaker` matches and whose conditions hold, and takes the highest `Priority`; two at the same priority is a data mistake, logged as a warning, and the lower primary asset ID wins so it is repeatable. With none it logs a warning and reports `Vestige.Feedback.Dialogue.NothingToSay` ("Nothing to say right now.", a `DA_FeedbackResponses` row), and returns false. Then it asks the relationship component to `RecordTalk(Speaker, Day)` (which marks the character met), holds the clock (`Hold(VestigeDialogue::ClockHold)`, [section 4](04-Time.md)), shows the first line and broadcasts `OnConversationStarted`, then `OnLineChanged`. "Met" is recorded when a talk starts, so a first meeting cut short with Escape still counts: you met.
- **Reading it:** `IsInConversation()`, `GetSpeaker()` (character data), `GetSpeakerActor()` (weak), `GetLineText()`, `GetChoiceTexts()` (the listed choices, empty for a plain line), `IsLastLine()` (for the box's "Close" hint).
- **Commands:** `Advance()` (to `Next`, or the end; does nothing while choices are listed), `Choose(int32 Index)` (Index counts the listed replies, those whose conditions hold, as `GetChoiceTexts` returns them; applies the choice's outcomes and goes to its `Next`; ignores a bad index), `EndConversation()` (ends now, Escape). Showing a line applies its outcomes. A `Next` that names no line ends the talk with an error (validation catches it first).
- **The end** releases the clock hold, clears the state and broadcasts `OnConversationEnded`. `EndPlay` ends a running talk the same way, so a map change or a destroyed player state never leaves the clock held.
- **Events** (native multicast, C++ listeners only for now): `OnConversationStarted`, `OnLineChanged`, `OnConversationEnded`. A Blueprint twin (`On Conversation Ended`, with the character) is added when a quest or mod first needs it.
- **Logging:** `LogVestigeDialogue` (`Characters/VestigeDialogueLog.h`): the talk chosen (Verbose), refusals and data mistakes (Warning).

**The farmer turns to the speaker.** `AVestigePlayerCharacter` follows its player state's conversation component while possessed; on `OnConversationStarted` it calls `FaceDirection` with the ground direction to the speaker actor. `FaceDirection(const FVector& WorldDirection)` is the one private function that aims the targeting component (`AimAt`) and sets the movement component's idle facing to the aim (`SetIdleFacing(Targeting->GetAimDirection())`); `DoMove` calls it too, so the pair isn't written twice. The movement component then turns the farmer as it does with no input (540 degrees a second, snapped to eight directions, so within 22.5 degrees of Hob). In a map without a grid the aim doesn't change, as when walking there. The farmer already faces Hob to start the talk, so the turn is small. The character binds to the conversation component in `PossessedBy` (the player state is set by then) and unbinds in `UnPossessed` and `EndPlay`. Test: `Vestige.Dialogue.TheFarmerTurnsToTheSpeaker` (after a talk starts, the movement component's idle facing points at the speaker within 22.5 degrees).

**Relationships: `UVestigeRelationshipComponent`** (`Characters/`, a component on `BP_PlayerState`). Owns, per character `FPrimaryAssetId`: whether the player has met them (saved) and today's talk count (`TalksToday`, kept with its day number, not saved: after a reload the day's greeting plays again, which the writer's lines allow). `HasMet(Character)`, `GetTalksToday(Character, Day)` (0 when the kept day isn't `Day`), `RecordTalk(Character, Day)`. It implements `IVestigeSaveable`: key `Base.Relationships`, version 1, `FVestigeRelationshipSaveData` with `TArray<FVestigeCharacterRelationshipSaveData>` (`Character`, `bMet`), registered in `BeginPlay` as the inventory does; a new game clears it. On load, a character the catalogue doesn't know is skipped with a warning and counted as left out ([Architecture.md, section 6](../Architecture.md#6-saving)).

- **Trust and flags.** Per character it also owns the earned trust points (`int32`, from `AddTrust`, never below 0) and the flags (`TMap<FGameplayTag, int32>`, each with the day it was last set). `AddTrust(Character, Amount)`, `SetFlag(Character, Flag, Day)`, `GetEarnedTrust(Character)`, `GetFlagDays(Character)` and `GetTrust(const UVestigeCharacterData&)`: the earned points plus, for each entry of the character's `TrustFromMilestones` that `UVestigeMilestoneSubsystem` has reached, its points. Trust from milestones is worked out when asked, never stored: a milestone reached before the player state exists (another map later, or before Hob is met) still counts, nothing can count twice, and a changed number in `DA_Character_Hob` applies to running games. There is no "step" in C++: a step is reached when its step talk plays and sets its flag (below). Trust and flag changes are logged at `Log` (`LogVestigeDialogue`: "Trust with Base.Hob is now 4 (+1)."), which is the play-test's readout; nothing is on screen.
- **Saving them:** `FVestigeCharacterRelationshipSaveData` gains `EarnedTrust` (`int32`, 0) and `Flags` (`TArray<FVestigeRelationshipFlagSaveData>`: `Flag`, the tag's `FName`, and `Day`), sorted by name so the same state writes the same bytes. A character is written when met, with earned trust or with a flag. The version stays 1: the fields are added with defaults that suit older records, which are tagged properties ([section 1](01-Saving.md)). On load, a flag whose tag no longer exists (`FGameplayTag::RequestGameplayTag(Name, false)` invalid) is skipped with a warning and counted as left out. A new game clears both.

**The farm's firsts: `UVestigeMilestoneSubsystem`** (game-instance subsystem, `Core/`): the game's one-time milestones, each a gameplay tag, reached once per game. `static Get(const UWorld*)`, `Reach(FGameplayTag)` (returns whether it was new; logs the first time at `Log` in `LogVestige`), `HasReached`, `GetReached()` (a container, for the context's copy). It knows no game rule; the owner of each event reaches its milestone, so the farm never knows who counts it: `UFarmingComponent::ReportCropHarvested` reaches `Vestige.Milestone.Farm.Harvested` (the one place every harvest is reported); `UFarmGameplayAbility_Harvest` reaches `Vestige.Milestone.Farm.Cleaned` in `ReportCleaning` when a harvest lowered its tile's level and `Vestige.Milestone.Farm.HarvestedMutated` when the tile's crop was mutated (copied before the harvest, as the item is); `UFarmGameplayAbility_Plant::UseOn` reaches `Vestige.Milestone.Farm.Planted` on every planting and `Vestige.Milestone.Farm.PlantedCleaningCrop` when the crop cleans (`GetContaminationCleanedPerHarvest() > 0`: Sinkwort in the base game, so a mod's cleaning crop would also open the Sinkwort topic, which is accepted until a mod has one); and `UFarmShippingSubsystem::SellShipment` reaches `Vestige.Milestone.Farm.Sold` when it paid more than 0 (the shipping subsystem takes it with `Collection.InitializeDependency<UVestigeMilestoneSubsystem>()` in `Initialize`, as it does the catalogue and the registry, and keeps the pointer; the farming component and the abilities, which have a world, use `Get`). The tags are native (`VestigeGameplayTags`, `AbilitySystem/`), since C++ reaches them; the sprinkler adds `Vestige.Milestone.Farm.SprinklerPlaced` when it is built, and Hob's tutorial and event lines read the same subsystem. It implements `IVestigeSaveable`: key `Base.Milestones`, version 1, `FVestigeMilestoneSaveData` (`TArray<FName> Reached`, sorted), registered with `InitializeDependency<UVestigeSaveRegistry>` and `RegisterGameOwner` as the field subsystem does; a new game clears it; an unknown tag on load is skipped with a warning and counted as left out. No event yet: trust reads it when a talk starts; an `OnMilestoneReached` comes with the first listener (Hob's event lines). In `Core/`, below `Farming/`, because farm code calls it and it knows nothing above the engine.

- **Topic gates and priorities** (H-04's table; the order is the game designer's, [GameDesign.md, section 8](../GameDesign.md#relationships): news before topics that are true on any day): SeasonEnd 64, Date Spring, days 19 to 25; Harvest 63, Milestone `Harvested`; Bin 62, Milestone `Sold`; Bloom 61, Milestone `HarvestedMutated`; Sinkwort 60, Milestone `PlantedCleaningCrop`; Planting 59, Milestone `Planted`; Dispensers 58, FarRows 57 and Well 56, none beyond `FromDay` 2. Each topic has its own priority because several are due at once from day 2.
- **The order reply changes from step 1.** A topic's order reply is entered twice, same text, its own `ReplyId` each: one listed with Flag `Step.Attentive` not set, going to `Answer.Order`, one listed with it set, going to `Answer.OrderView`; only one is ever listed, so a topic holds four entries and lists three (validation allows it: the two order entries carry conditions). Ask and leave replies are the same at every step. The replies keep the writer's order (the ask reply isn't always first). No branching lines are added.
- **H-05's two line 2s** are two assets with the same lines 1, 3 and 4 (the same string table keys), told apart by Flag `Asked`, which every ask reply sets; the one after an ask has the higher priority, so with `Asked` set it wins and without it only the other holds.
- **The greetings join, not replace.** Each band's warmer asset holds H-02's texts for that band plus H-08's (and, after the memory, H-08's last three lines too) in one pool, so a pool's no-repeat rule still holds. A merged pool has an ID of its own (`Hob.Greet.Warm.Morning`, `Hob.Greet.Memory.Morning`) while its texts keep their writer's keys, and the order reply entered twice has its own `ReplyId` for the second entry (`...Reply.OrderView`) with the first's text key, so the key tests (a text's key starts with its line's ID, a reply's key is its `ReplyId`) allow these two cases.
- **When a talk counts as played.** H-05 and H-07 set their flag on line 1, as the writer asks (Escape after line 1 counts). H-06 sets its step flag only on a reply, and its "offered" flag on line 1, so an offer ended with Escape before a reply comes back on a later day, not the same one. A topic's spacing flag is set on its opening, so an unanswered topic still spaces the topics, and its own flag only on a reply, so it comes back on a later day.
- **Steps in order.** Each step needs the step before set at least a day ago, so two steps reached at once play on consecutive days, lower first. Priorities differ wherever two conversations can hold at once (the tie warning stays a data mistake).
- **The watered line against topics and greetings.** The first watered morning outranks a due topic (the topic waits a day), because that morning is when the player links the dark soil to H-06; later watered mornings rank below topics, so the daily line never pushes the topics out. Every watered line sets `WateredMentioned`, and a later one plays only when it wasn't set in the last 2 days, so it comes at most every third watered morning and the warm greetings play on the others (the game designer's rule, GameDesign section 8).

**Layers:** the milestone subsystem in `Core/`; the data classes and conditions in `Content/`; the two components, the `AddTrust` and `SetFlag` outcomes and the log in a new layer, `Characters/`, above `Farming/` and below `Save/` ([Architecture.md, section 14](../Architecture.md#14-dependencies)), with the speaker's body ([section 10](10-Robots.md)). `Player/` (the player state adds the components) and `UI/` (the box) are above it.

**Performance:** nothing ticks. Choosing a talk is one loop over the dialogue assets on a key press; a line change is a few `FText` copies. All dialogue is in memory from the start of the game (text only, loaded by the catalogue), so nothing loads during a talk. `StartConversation` has a `TRACE_CPUPROFILER_EVENT_SCOPE`.

**Pitfalls:**

- Writing lines in C++ or Blueprint string literals, or setting an `FText` from a plain string in an asset script (culture-invariant, never translated).
- Branching dialogue as a big Blueprint graph per character; it can't be reviewed, localized or modded.
- Renumbering or reusing a line ID: it is the translation key and, later, the seen-line ID.
- A condition with side effects or a load: it runs for every candidate conversation on every talk.
- Forgetting to release the clock hold on every way a talk ends (the end of the lines, Escape, `EndPlay`).
- Setting a talk's "played" flag without deciding what Escape does: on line 1 the talk is lost if cut short, on a reply it plays again. Follow what the writer's file says for that talk.
- Storing trust from a milestone when it is reached: it misses milestones reached while no relationship component exists and can count one twice. Work it out when asked.
- A game rule telling the relationship component about a farm event: the farm would know about characters. Reach a milestone instead.
