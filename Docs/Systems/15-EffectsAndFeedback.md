# 15. Visual effects and feedback

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** no effects yet. Feedback reports are built (M4, 2026-11-08, below): gameplay reports tags and the HUD shows the text `DA_FeedbackResponses` gives each.

**References:** Epic's "Niagara" pages, including scalability and effect types; Lyra's gameplay cues and `ULyraContextEffectComponent` (effects chosen by surface type and context tags).

**Rules:**

- **Effects react to events**, like audio. Game code never spawns a particle system.
- **Niagara systems use effect types** with scalability settings and culling distances, so effects shrink or disappear at lower scalability and distance.
- Short, frequent effects are pooled (Niagara's pooling method on the spawn call).
- Effects are soft references in content data and load with the content that uses them.
- **Gameplay reports what happened; presentation picks the response.** Game code reports a feedback tag (`Vestige.Feedback.*`) with its values through `UVestigeFeedbackSubsystem::Report` and never writes the player's text; the HUD's `DA_FeedbackResponses` turns the tag into text (feedback reports, below). A use that worked reports nothing: it is already an event (`On Tool Used`, `On Crop Harvested`), and its sound and animation come through gameplay cues ([section 9](09-AbilitySystem.md)).

**Pitfalls:**

- Large translucent particles filling the screen (smoke, haze): use fog and post-processing for the haze ([Architecture.md, section 10](../Architecture.md#10-performance-by-design)).
- A sentence for every success ("Tilled the soil.", "Watered."): holding E filled the five message boxes in a few seconds ([CodeReview.md, M4](../CodeReview.md#m4--gameplay-code-writes-the-players-text)).

**Feedback reports** ([CodeReview.md, M4](../CodeReview.md#m4--gameplay-code-writes-the-players-text), 2026-11-08, approved by a senior Unreal C++ reviewer agent after two rounds of review, whose approval counts as David's). Gameplay reports *what happened* as a gameplay tag with named values, and the HUD looks the tag up in a data asset to pick the text.

References: Lyra's `ULyraGameplayAbility::FailureTagToUserFacingMessages` (a `TMap<FGameplayTag, FText>` on the ability, looked up in `NativeOnAbilityFailedToActivate` and broadcast as `FLyraAbilitySimpleFailureMessage` on the Gameplay Message Router) and `FLyraVerbMessage` (a verb tag plus instigator, target, tags and a magnitude, which `ULyraHealthSet` broadcasts on damage); Epic's "Gameplay Tags" and "Text Localization" pages (`FText::Format` with named arguments).

*Take, skip, change from Lyra:*

- **Take:** the reason is a gameplay tag and the text is looked up by tag, so new reasons are data and code never builds a sentence; Lyra's verb message's idea of a tag plus values instead of a finished string.
- **Skip:** the Gameplay Message Router plugin (Lyra's, not the engine's): one channel with one listener needs no bus, and [Architecture.md, section 4](../Architecture.md#4-how-systems-talk-to-each-other) keeps it for when many unrelated senders and listeners appear. Skip the per-player target and replication: single-player.
- **Change:** Lyra keeps the text map on each ability, a gameplay asset; ours is one presentation asset on the HUD, since M4 asks that presentation picks the text, and the reports also come from outside abilities (rest, saving, the day). Our tool failures happen inside an active ability (the target can't be worked), not at activation, so they are reported by the base tool ability, not from `NativeOnAbilityFailedToActivate`.

*Classes:*

- **`FVestigeFeedbackReport`** (plain C++ struct, `Core/VestigeFeedbackSubsystem.h`): `FGameplayTag Tag` and `FFormatNamedArguments Arguments` (the values the text may use, such as `Day`). Not a `USTRUCT`: only native delegates carry it.
- **`UVestigeFeedbackSubsystem`** (world subsystem, `Core/`): `static void Report(const UWorld* World, const FGameplayTag& Tag, FFormatNamedArguments Arguments = {})`, and `OnFeedback` carries `const FVestigeFeedbackReport&`. It logs every report to `LogVestigeFeedback` at `Log` as the tag and its values (`Vestige.Feedback.Day.Slept Day=2`), so the log keeps the history whatever the HUD shows. The values are turned into text by a helper in the subsystem's `.cpp` (`Name=` plus `FFormatArgumentValue::ToFormattedString(false, false)` for each, joined by spaces), called inside the `VESTIGE_LOG` arguments, so nothing is built while the category is off ([section 21](21-Logging.md)). An invalid tag logs a warning and is not broadcast.
- **Native feedback tags** in `AbilitySystem/VestigeGameplayTags.h`, with `UE_DEFINE_GAMEPLAY_TAG_COMMENT` (each comment names the reporter and its values), under `Vestige.Feedback` (no parent tag is declared: nothing names it, and the `Categories` meta is a string):

   Every morning has one day message: a season's first morning reports the season form of the day's tag rather than a second message, so the announcement isn't said twice, and a season's last day reports its last-day form (`Day.Slept.LastDay`, `Day.StayedUp.LastDay`), because `FText`'s plural keywords are CLDR's (`zero`, `one`, `two`, `few`, `many`, `other`, checked in 5.8's `TextFormatArgumentModifier.cpp`) and English puts 0 in `other`, so "0 days left" can't become "last day" in the text. Each form is a child tag of its event (`Day.Slept.NewSeason`, `Day.Slept.LastDay`, `Day.StayedUp.NewSeason`, `Day.StayedUp.LastDay`, `Save.Loaded.LastDay`), so a listener that cares only that the player slept matches the parent (`MatchesTag(Day.Slept)`), while the HUD looks the exact tag up (every row exists, `EveryFeedbackTagHasAResponse`). The reporter maps the calendar's `FVestigeCalendar::GetDayKind` (`Usual`, `NewSeason`, `LastDay`) and how the night ended to the tag; it never decides the order itself. Every day report carries `DaysLeft`; whether a text uses it is the responses' choice. A renamed native tag needs a `GameplayTagRedirects` entry for the keys in `DA_FeedbackResponses`. A use that worked reports nothing, so the successes ("Tilled the soil.", "Watered.") have no tag. `Save.Saved`'s text is David's (2026-11-08); an autosave icon can replace it later without a build. "No FarmGrid in the level..." is a setup error the player can't fix, so it is a log warning only ([section 21](21-Logging.md): logs aren't feedback).
- **`UVestigeFeedbackResponses : UDataAsset`** (`UI/`, `Const`), the asset `Content/Vestige/UI/DA_FeedbackResponses`: `TMap<FGameplayTag, FVestigeFeedbackResponse> Responses` (`EditDefaultsOnly`, `meta = (Categories = "Vestige.Feedback", ForceInlineRow)`), where `FVestigeFeedbackResponse` is a `USTRUCT(BlueprintType)` with `FText Message` (empty shows nothing); `BlueprintType` only so editor scripts can make and set rows, as on `FFarmCropGrowthStage`, and Blueprints don't read it. A struct rather than a bare `FText`, because the sound for a report joins the same row when audio arrives ([section 14](14-Audio.md)), as Lyra's second map (`FailureTagToAnimMontage`) shows a reason has more than a text. `FindResponse(const FGameplayTag&)` returns the row or `nullptr`, and the static `FormatMessage(const FVestigeFeedbackResponse&, const FVestigeFeedbackReport&)` formats its text with the report's arguments (`FText::Format(Message, Arguments)`). `IsDataValid` reports a key that is invalid or isn't a tag the tag manager knows (`UGameplayTagsManager::RequestGameplayTag(Name, false)`); whether each text uses only the values its reporter gives is checked by a content test (below). Its texts are gathered for translation from the asset, as any asset text.
- **`AVestigeHUD`** has `UPROPERTY(EditDefaultsOnly, Category = "HUD") TObjectPtr<const UVestigeFeedbackResponses> FeedbackResponses`, set on `BP_HUD` (a hard reference: the asset is a few dozen texts, needed as soon as the HUD shows). `ShowFeedback(const FVestigeFeedbackReport&)`, bound to `OnFeedback`, finds the row and shows its formatted text when the text isn't empty, and does nothing for an empty one. A report with no row logs a warning (`LogVestigeFeedback`, naming the tag and the asset with `GetNameSafe(FeedbackResponses)`) and shows nothing; with no asset set, the HUD logs an error at `BeginPlay`, as for a missing widget class, and shows no messages. Test-only getter: `GetFeedbackResponses()`.

*Reporting in gameplay:*

- **Tool abilities.** `CanUseOn` gives the reason: `virtual bool CanUseOn(const FIntPoint& Tile, FGameplayTag* OutFailureReason) const` (no default argument, since it is virtual), which sets the reason when it returns false and the pointer isn't null. When several reasons apply, each ability reports the first of these that applies:
   - Till: no tile state, `Tool.NoTarget`; otherwise `Farm.CantTill`.
   - Plant: no seed in hand first, `Farm.NothingToPlant`, then no tile state `Tool.NoTarget`, then `Farm.CantPlant`. Its `CanUseOn` checks the seed before the tile, in that order.
   - Water: no tile state `Tool.NoTarget`; otherwise `Farm.CantWater`.
   - Harvest: no tile state `Tool.NoTarget`, then not ripe or no crop `Farm.NothingRipe`, then no room `Inventory.Full`.

   `UseOn(const FIntPoint& Tile)` does the work and returns whether the farm changed; it reports nothing. The base ability's first try after a press asks `CanUseOn(Target, &Reason)` before `UseOn`, as a repeat does, with `Reason` empty first. When it is false the base sets `Step = Using` (a listener may end the ability, as during `UseOn`), reports `Reason` through a private `ReportFeedback(const FGameplayTag&)` (only the base reports), returns if the ability is no longer active, and otherwise waits for another target or ends, as a use that changed nothing does. A `CanUseOn` that returns false with no reason is a bug in that ability: `ensureMsgf` naming the ability's class, and nothing is reported. A repeat passes `nullptr` and stays quiet. Nothing runs between `CanUseOn` and `UseOn`, so `UseOn` returning false after `CanUseOn` passed means the two disagree: the base logs a warning (`VESTIGE_LOG(this, LogFarm, Warning, ...)` with the ability's class and the tile), reports nothing and treats it as a use that changed nothing. "No tile" on the press reports `Tool.NoTarget`. The harvest ability's `UseOn` keeps its check for room before harvesting, so a full bag never destroys a crop. `ReportFeedback` returns whether the ability is still active, and the subclasses set their reason with the base's protected static `FailBecause(OutFailureReason, Reason)`, which returns false.
- **Everyone else** calls `Report(World, Tag)` or, with a date, `Report(World, Tag, Clock->GetCalendar().GetReportValues(Day))`, which gives `Day`, `Season` and `DayOfSeason` ([section 4](04-Time.md), the calendar): the farming component (`ReportNothingInHand`), the stamina set, the rest component, the game mode and the save subsystem, which keeps its reports (`PendingReports`) until the map has begun play and refuses to save with the reason's tag. No player message is a `LOCTEXT` in gameplay code.
- **Not reports:** the interaction options' labels ("Sleep", "Harvest"), which stay with the interactables, which own what they offer ([section 7](07-Interaction.md)), the HUD's own texts (status, stamina, bag, hints), and data validation messages, which are editor text for developers.

*Data:* `DA_FeedbackResponses` holds the rows above. The editor gives each text a stable localization key, with the package's namespace, when it saves the asset.

*Tests:* `Vestige.Feedback.*` (a report reaches every listener; an invalid tag isn't broadcast), the farming tests for the reasons on a press and silence for a use that worked or a quiet repeat, the game mode's day reports, the rest warnings, `Stamina.Empty` reported once, and the response's formatting (`Vestige.UI.TheFeedbackResponsesFormatTheReport`). `Vestige.UI.EveryFeedbackTagHasAResponse`: `BP_GameMode`'s HUD class's `GetFeedbackResponses()` is set (read as `VestigeHudWidgetTests.cpp` reads the widget class) and has a row for each native feedback tag, listed in the test with the argument names its reporter gives (`Day`, `Season`, `SeasonInSentence`, `DayOfSeason` and `DaysLeft` for `Day.Slept`, `Day.StayedUp`, their last-day forms, `Save.Loaded` and `Save.Loaded.LastDay`, those and `PreviousSeason` for `Day.Slept.NewSeason` and `Day.StayedUp.NewSeason`, none for the rest), and no other row. `RequestGameplayTagChildren` isn't used: it also returns the in-between tags (`Vestige.Feedback.Farm`). Every row has text, and each text is a valid format (`FTextFormat::IsValid`) whose argument names (`GetFormatArgumentNames`, case-sensitive) are all among its tag's, so a `{day}` typo fails. A HUD that shows nothing for a report without a row needs a local player, which the test spawner can't make, so it is checked by hand.

*Known gaps,* recorded as deferrals in the decision log entry: a mod can't add a reason without replacing the base asset, since our tags live under `Vestige.` and mods add their own root ([Architecture.md, section 12](../Architecture.md#12-designing-for-mods)); later, response assets found through the Asset Manager and merged by the HUD. Blueprints can neither report nor listen; a Blueprint-callable `Report` and a dynamic twin of `OnFeedback` come with the first Blueprint or mod that needs them.
