# 9. Abilities, attributes and effects (Gameplay Ability System)

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** adopted 2026-10-29, starting with stamina (milestone 2, [Roadmap 4.3](../Roadmap.md#43-stamina-and-late-nights)); David approved the stamina design on 2026-10-29. Built: stamina, tool use as an ability with its cost and the slower uses at zero, the refill on sleep and saving (2026-11-01); the late-night rules (2026-11-02, agreed with David), with the drain on the clock's game minutes since [M7](../CodeReview.md#m7--game-time-events-run-on-real-time) (2026-11-11); each tool's behaviour as its own ability, and the stamina effects as `GE_` assets named by the game data (both 2026-11-07, below). Health and combat (milestone 3) build on the same setup.

**References:** Epic's "Gameplay Ability System" pages (ability system component, attribute sets, gameplay effects, gameplay abilities, ability tasks, gameplay cues); Lyra's setup: `ULyraAbilitySystemComponent` on the player state, `ULyraAbilitySet` data assets that grant abilities, effects and attribute sets together, attribute sets such as `ULyraHealthSet`, abilities with an activation policy, and gameplay cues for cosmetics.

**Rules:**

- **The ability system component lives on the player state** for the player (so attributes survive the pawn), and on the pawn for robots and creatures that don't have a player state. The pawn's avatar is set when it's possessed.
- **Attributes in attribute sets** (`UVestigeStaminaSet`, later `UVestigeHealthSet`), with clamping in `PreAttributeChange` and reactions in `PostGameplayEffectExecute`. Attributes change **only through gameplay effects**, never by setting the value from outside.
- **Gameplay effects as data**: costs (a tool's stamina cost becomes a cost effect), buffs, over-time drains (late-night drain), with magnitudes from data, not code.
- **Abilities granted from ability set data assets**, as Lyra does, so a tool, item or robot type grants its abilities by data.
- **Gameplay tags drive state**: blocking (`Vestige.State.Exhausted` blocks sprinting), cooldowns and activation rules, with native tags ([section 3](03-GameplayTags.md)).
- **Cosmetics through gameplay cues**, not inside abilities ([section 15](15-EffectsAndFeedback.md)).
- Single-player: no prediction keys or replication modes beyond the defaults; the ability system component uses minimal replication settings.
- Saving: save attribute base values and active long-lived effects by ID; restore them through effects or the set's restore function, not by writing attributes directly.

**Setup:** the Gameplay Abilities plugin is enabled in `Vestige.uproject`, and `GameplayAbilities` and `GameplayTasks` are private dependencies in `Vestige.Build.cs` (`GameplayTags` was already there). Our ability system code lives in its own layer, `Source/Vestige/AbilitySystem/`, right above `Core/`, so content (an item that grants abilities) can include it later; the folder isn't called `Abilities/` because the plugin's own headers are included as `Abilities/...`. Lyra calls `UAbilitySystemGlobals::Get().InitGlobalData()` from its asset manager; in Unreal Engine 5.8 that isn't needed, because the plugin calls it itself the first time the globals are asked for (`GameplayAbilitiesModule.cpp`). `DefaultGame.ini` names `/Game/Vestige/Abilities` as the folder for gameplay cue notifies, so the engine doesn't scan all of `/Game` for them.

**Native tags** are declared in `AbilitySystem/VestigeGameplayTags.h` (`VestigeGameplayTags::Ability_UseTool`, `State_UsingTool`, `Ability_Interact`, `Data_StaminaCost`, `Data_StaminaDrain`, `Data_StaminaRefill`, `State_OutOfStamina`, `State_Exhausted`), and so are the input tags (`Input_*`, [section 5](05-Input.md)), so code never builds a tag from a string. Tags only content uses stay in `DefaultGameplayTags.ini` ([section 3](03-GameplayTags.md)).

**First use: stamina.** The rules in [GameDesign.md, section 5](../GameDesign.md#5-time-days-and-seasons) mapped onto the system:

| Rule | Built as |
|---|---|
| The player has stamina, shown on the HUD | Built. `UVestigeStaminaSet` with `Stamina` and `MaxStamina` (100 at the start, a named constant until characters get starting stats from data), on the ability system component of `AVestigePlayerState`. The HUD listens to both attributes' change delegates and shows "Stamina 85 / 100", in red while the ability system holds `Vestige.State.OutOfStamina`: the HUD follows the tag (`RegisterGameplayTagEvent`) rather than the number, so the set alone decides when stamina has run out, and it recolours the line only when the tag changes |
| Tool actions cost stamina | Built. Using a tool is a gameplay ability: the tool's own (`UFarmGameplayAbility_Till`...), on the shared base `UVestigeGameplayAbility_UseTool`. Its cost is `GE_StaminaCost`, named by the game data (`UVestigeGameData`), whose magnitude is the tool's `StaminaCost`, passed as a set-by-caller value tagged `Vestige.Data.StaminaCost`. A use that changes nothing on the farm (no target, nothing to water) costs nothing |
| Stamina never goes below zero; at zero, actions still work but take twice as long | Built. The set clamps `Stamina` to 0..`MaxStamina`. While it is 0, the set holds `Vestige.State.OutOfStamina` on the ability system as a loose tag, and tells the player once when it runs out. Each use takes the tool's `UseSeconds`, `OutOfStaminaTimeScale` (2) times as long while the tag is held; the ability stays active that long, so the next use can't start. Costs are still applied, and clamp at 0. The ability's `CheckCost` always passes, so a cost never blocks an action |
| Stamina drains faster after midnight | Built. There is no daytime drain, so this is a drain that starts at midnight: `GE_LateNightDrain`, an instant effect that adds a set-by-caller amount tagged `Vestige.Data.StaminaDrain`. The rest component applies it on each of the clock's `OnMinuteStarted` after its `LateNightHour` (24), for the minute just passed, with a minute's share of `LateNightDrainPerGameHour` (10). So the drain follows game time ([M7](../CodeReview.md#m7--game-time-events-run-on-real-time), 2026-11-11): a skip drains as if the time had passed, a stopped clock drains nothing, and the clock's speed doesn't change the drain per game hour. Nothing drains at the midnight instant, and 00:00 to 06:00 drains 60 |
| Going to bed late makes the player exhausted: next day at 75%, one level, cleared by a night in bed before midnight | Built. A night that ends at `LateNightHour` or later (sleeping then, or staying up until the day ends at 06:00) applies `GE_Exhausted`, an infinite effect with no modifiers that grants `Vestige.State.Exhausted` through a target tags component, unless the player is already exhausted. The refill is then `ExhaustedRefillFraction` (0.75) of `MaxStamina`. A night that ends earlier refills fully and removes the effect. The HUD shows "Exhausted" after the stamina while the tag is held |
| Sleep refills stamina | Built. `GE_StaminaRefill`, an instant effect that overrides `Stamina` with a set-by-caller amount tagged `Vestige.Data.StaminaRefill`: the rest component sets it to `MaxStamina` times the night's refill share and applies it just before it starts the next day, so it is saved state changed synchronously ([Architecture.md, section 15](../Architecture.md#15-the-day-flow)). The set clamps the result |

Who owns what: `AVestigePlayerState` owns the ability system component and grants its ability sets in `PostInitializeComponents`, so the stamina set exists before any actor's `BeginPlay`; it makes the pawn the avatar when `OnPawnSet` fires, and cancels running abilities when the pawn changes. The pawn (`AVestigePlayerCharacter`) implements `IAbilitySystemInterface` and returns the player state's component, so lower layers find it with `UAbilitySystemGlobals::GetAbilitySystemComponentFromActor` without knowing the player state class. `UVestigeStaminaSet` owns the numbers, their limits and the out-of-stamina tag. The farming component finds the tool of the item in hand (the inventory's hotbar, [section 8](08-Inventory.md)) and grants its ability, and grants the harvest all the time ([section 7](07-Interaction.md), harvesting with F), and `UFarmTargetingComponent` keeps the target tile; the tool abilities own what a use does, what it costs and how long it takes (tools as abilities, below). `UVestigeRestComponent` on the player state owns sleep, the late-night rules (the warnings at 22:00 and midnight, the drain), exhaustion and the refill, and its settings hold their numbers. Abilities and the stamina set are granted from a `UVestigeAbilitySet` data asset (`Content/Vestige/Abilities/DA_AbilitySet_Player`, named on `BP_PlayerState`): a plain list of attribute set classes and ability classes, without Lyra's grant handles until something needs to take a set away. Saving stores the base value of `Stamina` (`FVestigeStaminaSaveData`) and restores it through the set's restore function, which sets the base value without replaying effects. Whether the player is exhausted is saved by the rest component (`FVestigeRestSaveData`), which applies the effect again on load. The drain keeps no state, so it needs no saving. Tests: the stamina, rest and farming tests cover every row of the table above, the save, and exhaustion in the save.

Choices the design left open, decided on 2026-11-01 (decision log):

- **The out-of-stamina tag is a loose tag the set keeps in step with `Stamina`, not an infinite effect.** It is derived from the number, so it can't drift from it, needs nothing in the save and no effect asset.
- **The refill's magnitude is an amount set by the caller** (2026-11-02), not `MaxStamina` read by the effect: an attribute-based magnitude's coefficient can't come from the caller, so a refill to 75% would need a second effect or a custom calculation class. The rest component multiplies `MaxStamina` by the night's share.
- **A tool use takes time.** "Twice as long" needs a duration, and there are no animations yet, so the tool's `UseSeconds` is how long a use lasts. The wait is a `WaitDelay` task, as [CodeReview.md, L3](../CodeReview.md#low) asked and [CodingGuidelines.md, section 12.3](../CodingGuidelines.md#123-memory-and-allocation) allows. With animations, the duration becomes the montage's length and the play rate halves at zero stamina.

**Tools as abilities** ([CodeReview.md, H1](../CodeReview.md#h1--the-gameplay-ability-system-gates-tools-but-doesnt-run-them), 2026-11-07, approved by a senior Unreal C++ reviewer agent after two rounds of review, which David accepted). A tool's behaviour is its own ability class, named by the tool's data asset, so a new tool is a new ability and a data asset, with no change to the farming component.

References: Epic's "Gameplay Abilities" and "Ability Tasks" pages (`UAbilityTask_WaitDelay`, `UAbilityTask_WaitMovementModeChange`), the ability's input hooks (`UAbilitySystemComponent::AbilitySpecInputPressed` / `AbilitySpecInputReleased`, `UGameplayAbility::InputReleased`, `FGameplayAbilitySpec::InputPressed`), and the spec's source object (`FGameplayAbilitySpec::SourceObject`, `UGameplayAbility::GetCurrentSourceObject`). Lyra: `ULyraEquipmentInstance` grants its equipment's ability sets when it is equipped and takes them away when it is unequipped, and its weapon abilities find their weapon through the spec's source object. Engine behaviour below was checked in the 5.8 source.

How it works:

- **The parts.** `UVestigeToolData::Ability` (`TSubclassOf<UGameplayAbility>`) is the ability that is the tool's behaviour, checked in `IsDataValid` (set, not abstract), next to `StaminaCost`, `UseSeconds` and `HeldMesh`; `Content/` sits below `Farming/`, so it names the engine's base class, and `Vestige.Content.EveryToolNamesAToolAbility` checks every tool names a `UVestigeGameplayAbility_UseTool`. That abstract base (`Farming/`) holds what every tool use shares and is not granted by `DA_AbilitySet_Player`. `UFarmGameplayAbility_Till`, `_Plant`, `_Water` and `_Harvest` hold one behaviour each and report a feedback tag when a use can't happen ([section 15](15-EffectsAndFeedback.md)); they take the `Farm` prefix, as farming actions ([CodingGuidelines.md, section 2.2](../CodingGuidelines.md#22-the-vestige-and-farm-project-prefixes)). The farming component grants the ability of the tool in hand and passes the use key's press and release to it; it includes the engine's ability system headers to grant, but none of our abilities.
- **Granted while in hand.** The farming component keeps the spec handle it granted and the ability system it granted it on (a weak pointer), and one function, `UpdateGrantedTool`, makes them match the tool in hand and the ability system the pawn reaches now (the player state's): it takes back the old grant through the stored pointer and gives the new tool's ability with the tool asset as the spec's source object. It runs when the tool in hand changes, on the use key's press, and when the pawn's controller changes (`APawn::ReceiveControllerChangedDelegate`, which fires after the pawn's player state is set or cleared), and `EndPlay` takes the grant back through the stored pointer. The pointer matters: by the time a pawn's components end play the pawn has already been unpossessed and its player state cleared, so the pawn no longer reaches the ability system, and without it each new pawn would leave a grant behind. An ability in the middle of a use when its tool leaves the hand is first told the key is released and then marked to be removed when it ends (`SetRemoveAbilityOnEnd`, which removes at once an ability that isn't active), so switching tools can't cut a use's time short; the new tool's ability is blocked until it ends (below). Granting costs one ability object per tool switch (instanced per actor), made on a key press, never per frame, plus two log lines at the ability system's Log level.
- **One press, one activation.** The use key's `Started` calls `StartUsingTool`, which marks the key held for the walk speed, grants if needed, sets the spec's input as pressed (`AbilitySpecInputPressed`) and tries to activate the spec by its handle. `Completed` calls `StopUsingTool`, which sets it released (`AbilitySpecInputReleased`); the engine passes that to the active ability's `InputReleased`. **Whether the key is held is read from the spec's `InputPressed` at every decision the ability makes**, never from a flag of its own or the component's: a press while a use is finishing can't start a second activation, but it does set `InputPressed`, so the repeat goes on. `UseTool` (one use, for tests and console commands) activates without pressing.
- **The loop inside the ability.** On activation, and each time a use finishes, the base ability tries the next use:
   1. In the air: if the key is held, wait for the farmer to walk again (`WaitMovementModeChange` to walking), then try again; otherwise end without a use.
   2. Read the target tile from the targeting component (`UFarmTargetingComponent`). No target: on the press only, report `Vestige.Feedback.Tool.NoTarget`; then wait for the target to change if the key is held, or end.
   3. Every try asks `CanUseOn` first. On the first try after the press, a `CanUseOn` that fails reports its reason ([section 15](15-EffectsAndFeedback.md)); a try after a landing counts as a repeat, and a repeat that would change nothing waits quietly for the target to change.
   4. A use that changed the farm commits the tool's cost (`CommitAbilityCost`), reports `On Tool Used` through the farming component, and waits the use's time with `WaitDelay`: the tool's `UseSeconds`, `OutOfStaminaTimeScale` (2) times as long while the player is out of stamina, read before the cost so the use that empties stamina runs at full speed. Then step 1 again if the key is held, or end.
   5. A use that changed nothing ends the ability if the key isn't held, or waits for the target to change.

   The ability keeps which of these it is doing (using, waiting out the use, waiting for the target, waiting for a landing) and sets it before calling out. `UseOn` and the reports run other code (the field's change event, Blueprint handlers of `On Tool Used`) that can move the farmer, switch tools or end the ability, so after each call out it stops if it is no longer active, and a target change that arrives while it isn't waiting for one is ignored (the next try reads the target anyway). It never keeps a pointer to its spec across a call that can end it: with remove-on-end set, ending removes the spec. Waiting for the target means listening to the targeting component's `OnTargetTileChanged`, through a weak pointer, removed in `EndAbility` before the base class's end. Releasing the key ends a waiting ability at once, and lets a use under way finish its time first. While the ability is active it owns `Vestige.State.UsingTool` (`ActivationOwnedTags`), and every tool ability is blocked by it (`ActivationBlockedTags`), which keeps one use at a time across tools. The tag means "a tool ability is active", which includes waiting idly with the key held, not "a use is under way", so animation must not key off it.
- **What a subclass writes.** `bool CanUseOn(const FIntPoint& Tile, FGameplayTag* OutFailureReason) const` (whether a use would change the tile now, changing nothing, and why not as a `Vestige.Feedback` tag, set with the base's `FailBecause`) and `bool UseOn(const FIntPoint& Tile)` (do it and return whether the farm changed; it reports nothing). The base gives them the field (`GetField`), the tool in use (`GetTool`, from the spec's source object), the inventory on the ability system's owner, the player state (`GetInventory`), and the farming component (`GetFarming`) for the reports. The tile work goes through the field's rule functions (`UFarmField::Till`, `Plant`, `Water`, `Harvest` and `GetTile`), which already are the interface between farming actions and the tiles, so no new interface is added on the grid. When a tool targets something other than a tile (a placed sprinkler, [section 16](16-PlacingAndBuilding.md)), that target kind gets an interface then.
- **Extension points stay on the farming component**, so Blueprints bind them as before: the harvest ability calls `UFarmingComponent::ReportCropHarvested` and the base ability `ReportToolUsed`, which broadcast `On Crop Harvested` and then `On Tool Used`. The ability calls the component; the component never calls our abilities.
- **Ability tasks, not timers.** The base waits with `WaitDelay` and `WaitMovementModeChange`, not an `FTimerManager` timer and the pawn's `LandedDelegate`, as [CodeReview.md, L3](../CodeReview.md#low) asks: standard tasks are what other Unreal developers expect to read, and montage tasks replace `WaitDelay` when tools get animations. It costs one small task object per use, at most about three a second while the key is held, made in the last task's callback. That is an exception to [CodingGuidelines.md, section 12.3](../CodingGuidelines.md#12-performance) (no new objects per action), recorded there: ability tasks are allowed per action, never per frame. A task that fires after its ability ended does nothing (it is marked garbage when the ability ends it).
- **Data.** The four tool assets name their ability (`DA_Tool_Hoe` Till, `DA_Tool_Seeds` Plant, `DA_Tool_WateringCan` Water, `DA_Tool_Hand` Harvest). `Ability` becomes a soft class reference in the tool's bundle once tool abilities can be Blueprints.
- **Input stays a native binding.** The use key binds to `UFarmingComponent::StartUsingTool`, which runs owner logic (following the inventory, granting the tool in hand, the held key for the walk speed) before it presses the spec; abilities activate by input tag ([section 5](05-Input.md)) only once a key maps straight to an ability with no owner logic in between.
- **Limits.** Mods can't add a tool yet: `CanUseOn` and `UseOn` are C++, and a Blueprint tool needs both Blueprint-implementable and the field's rules callable from Blueprints ([Roadmap.md, 4.0](../Roadmap.md#40-structure-from-the-code-review), H1's modding half). A landing in a movement mode other than walking (swimming, nav walking) doesn't resume a held use; releasing the key still ends it. Revisit with water or navigation.

Tests (`Source/Vestige/Tests/`): the farming tests cover each tool's rules, costs, one use at a time, the slowdown at zero stamina, holding and releasing the key, the air, the extension points). The test world isn't ticked by the engine, and ticking it would run the farmer's movement (he would fall, as the test level has no floor), so the tests that hold the key run as latent steps (`TestCommandBuilder`) that advance only the world's timer manager, once per step, until the use's time has passed. Single-use tests still end the use directly. "A use is under way" is read from `Vestige.State.UsingTool`. `ANewPawnLeavesNoToolAbilityBehind` possesses a second farmer with the same controller, so the controller-changed path runs, and `ANewToolNeedsOnlyItsAbility` works the tile with a test ability on a transient tool asset.

**Effects as `GE_` assets** (the second half of [CodeReview.md, H1](../CodeReview.md#h1--the-gameplay-ability-system-gates-tools-but-doesnt-run-them), 2026-11-07, approved by a senior Unreal C++ reviewer agent after two rounds of review, whose approval counts as David's). The four stamina effects are gameplay effect Blueprints, as Epic's documentation and Lyra make them, so a designer or a modder can change what they do (give the drain a period again, make exhaustion also lower the maximum, add a gameplay cue), and code finds them through one global data asset. The numbers that are rules stay with their owners: the tool's `StaminaCost`, the rest component's drain per game hour and refill share, `MaxStamina` in the set.

References: Epic's "Gameplay Effects" page (effects are data: a Blueprint class whose parent is `UGameplayEffect`, edited in its Class Defaults; set-by-caller magnitudes; gameplay effect components such as the target tags component), and Lyra's `ULyraGameData` (one `UPrimaryDataAsset` of global data, `DefaultGameData`, that names the set-by-caller damage and heal effects) loaded once by `ULyraAssetManager` from a config path (`LyraGameDataPath`) at startup, with an always-cooked primary asset type so the cook includes it. Engine behaviour below was checked in the 5.8 source.

| Part | Kind | Owns |
| --- | --- | --- |
| `GE_StaminaCost`, `GE_StaminaRefill`, `GE_LateNightDrain`, `GE_Exhausted` | Gameplay effect Blueprints, parent `UGameplayEffect` (`Content/Vestige/Abilities/`) | Cost is instant and adds `Vestige.Data.StaminaCost` to `Stamina`; refill is instant and overrides `Stamina` with `Vestige.Data.StaminaRefill`; the late-night drain is instant and adds `Vestige.Data.StaminaDrain`; exhausted is infinite with no modifiers and a target tags component granting `Vestige.State.Exhausted` |
| `UVestigeGameData` | `UPrimaryDataAsset` (`Content/`), one asset: `Content/Vestige/DA_GameData` | Global data game code needs that isn't one piece of content. For now the four effects game code applies, as `TSubclassOf<UGameplayEffect>` (`StaminaCostEffect`, `StaminaRefillEffect`, `LateNightDrainEffect`, `ExhaustedEffect`). `Get()` returns the loaded asset. `IsDataValid` reports an unset effect and a drain that isn't instant |
| `UVestigeAssetManager` | Asset manager (`Content/`), `Config = Game` | `GameDataPath` (a `TSoftObjectPtr<UVestigeGameData>` set in `DefaultGame.ini`), loaded once in `StartInitialLoading`, after the base class, and kept in a `Transient` `UPROPERTY` so it stays loaded. `GetGameData()` |
| `UVestigeRestComponent`, `UVestigeGameplayAbility_UseTool` | (`Farming/`) | Apply the game data's effects, with their set-by-caller values |

How it works:

- **Loaded at startup, never during play.** The game data holds hard class references, so loading it loads the four effects with it, a few kilobytes that every game needs. Lyra holds soft references and resolves them with `UAssetManager::GetSubclass`, which loads synchronously on first use, during play; hard references avoid that ([CodingGuidelines.md, section 12](../CodingGuidelines.md#12-performance)). `StartInitialLoading` runs once per process (from `UEngine::InitializeObjectReferences`), before any world, in the game, the editor and commandlets, so tests and Play in Editor find it loaded; native gameplay tags are registered by then, and the engine loads its own Blueprint game singleton at the same point. The one exception is `-SkipAssetScan`, which skips it: the game then runs without the effects, as below. The load is synchronous and happens once, at startup.
- **Missing data doesn't crash.** If `GameDataPath` doesn't load, the asset manager logs an error (`LogVestigeContent`) and `Get()` returns the class default object, whose effects are all unset; Lyra stops the game instead, but a broken mod or a half-made asset shouldn't. `Get()` is built on `UAssetManager::GetIfInitialized()` and a `Cast` (never `UAssetManager::Get()`, which stops the engine when there is no asset manager), falling back to the class default object, so it also works with another asset manager class or none. The cost, the refill and the drain check the spec they make (`MakeOutgoingSpec` returns an invalid handle for a null class); exhaustion makes no spec, so the rest component checks the class before applying it and takes its class default object with `TSubclassOf::GetDefaultObject`, never `GetDefault<UGameplayEffect>(Class)`, which crashes on null. With an effect unset nothing changes stamina and nothing logs every night: uses cost nothing, the night doesn't drain or exhaust, sleeping doesn't refill. `Get()` is a cast and a pointer read, cheap enough per tool use.
- **Cooked.** `DefaultGame.ini` gets a primary asset type `VestigeGameData` (base class `UVestigeGameData`, the one specific asset `/Game/Vestige/DA_GameData`, `CookRule=AlwaysCook`), as Lyra registers `LyraGameData`: a path in config alone isn't found by the cook. The asset is a primary asset by its class name, which `UPrimaryDataAsset` gives it.
- **The cost.** A C++ ability can't name a Blueprint effect in its constructor without a hard-coded path, and its class default object is made before the game data loads, so `CostGameplayEffectClass` stays unset. `ApplyCost` makes its spec from the game data's `StaminaCostEffect` (with `MakeOutgoingGameplayEffectSpec`), and `GetCostGameplayEffect` is overridden to return that effect's class default object, so engine code and debug tools that ask an ability for its cost see it. `CheckCost` always passes.
- **The drain has no period.** It is an instant effect the rest component applies on each of the clock's game minutes after midnight (the stamina table above); the rest component checks once, at `BeginPlay`, that the effect is instant, logs an error and drains nothing if it isn't, and `IsDataValid` checks the same in the editor.
- **Exhaustion** is applied with the game data's `ExhaustedEffect` (`ApplyGameplayEffectToSelf` with its class default object, after checking the class is set) and removed with `RemoveActiveGameplayEffectBySourceEffect` on the same class, so the rest component, its save restore and `StartNewGame` all name one class.
- **The tags are the contract.** `Vestige.Data.StaminaCost`, `StaminaRefill` and `StaminaDrain` stay native tags: code sets them on every spec, and an effect asset reads them or not. A designer who changes an effect's magnitude to something else (a scaled attribute, a curve) just stops reading the tag: setting a value an effect doesn't read is silent. The other way round is an error: an effect that reads a set-by-caller tag nobody set logs one (`LogGameplayEffects`) and uses 0, so a new tag needs the code that sets it.
- **Saves store values, never effects:** the base value of `Stamina` and whether the player is exhausted.

Later: per-tool cost effects (a tool whose use costs something other than stamina gets a `CostEffect` on its data asset when one exists), starting stamina from data ([Roadmap.md](../Roadmap.md), 4.3), and gameplay cues.

Tests: the stamina, rest, farming and save tests apply the real assets through `UVestigeGameData::Get()`. `Vestige.GameData.NamesEveryEffect` checks the loaded game data is the asset at `GameDataPath`, every effect is set and it passes `IsDataValid`, and `Vestige.GameData.ADrainThatIsntInstantIsInvalid` checks validation catches a drain that isn't instant.

**Pitfalls:**

- Building more of the system than stamina needs. Start with the stamina set, the tool abilities, the effects above and one ability set; add Lyra's extras (custom ability system component subclasses, activation groups, ability cost classes) only when a second use needs them.
- Abilities that tick or poll. Use ability tasks, timers and attribute change delegates.
- Setting an attribute from outside its set. The set exposes only getters; its `Init` helpers are private and only its constructor uses them. Loading goes through the set's restore function.
- Instancing policy: use instanced-per-actor abilities (non-instanced abilities are deprecated in recent engine versions); avoid instanced-per-execution, which creates an object on every use.
- Making `GE_` assets with editor Python: it can't set a modifier's attribute (a field path). A temporary headless commandlet can; the reviewer reviews the commandlet, since the asset diff is binary.
