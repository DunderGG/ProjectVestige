# 2. Content and the Asset Manager

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** built for crops, tools and items (`UVestigeContentData`, `UFarmCropData`, `UVestigeToolData`, `UVestigeItemData`). `UVestigeContentData::IsDataValid` checks the ID format, and `UVestigeAssetManager` reports duplicate IDs after the initial asset scan. The global game data is built (2026-11-07): `UVestigeGameData` (`DA_GameData`), loaded once at startup, names the gameplay effects code applies ([section 9](09-AbilitySystem.md)). The content catalogue is built (2026-11-08, below): `UVestigeContentCatalog` loads every content definition once per game, and every system finds content there. The ID redirect list is deferred until an ID has to change.

**References:** Epic's "Asset Management" and "Data Assets" pages (`UPrimaryDataAsset`, primary asset types in Project Settings > Asset Manager, asset bundles, `UAssetManager::LoadPrimaryAsset`); Lyra's `ULyraAssetManager` (a project subclass that loads global game data at startup) and its data assets (`ULyraPawnData`, `ULyraExperienceDefinition`, `ULyraInventoryItemDefinition`).

**Rules:**

- One `UVestigeContentData` subclass per kind of content, one asset per piece of content, registered as a primary asset type in `Config/DefaultGame.ini` and found through the Asset Manager ([Architecture.md, sections 5 and 12](../Architecture.md#5-data-and-content)). Each type is scanned in its own folder and always cooked: `FarmCrop` in `Content/Vestige/Crops`, `VestigeTool` in `Content/Vestige/Tools`, `VestigeItem` in `Content/Vestige/Items`; the global game data is the one asset `Content/Vestige/DA_GameData`.
- Definitions hold no runtime state. Per-instance state (a crop's growth, an item's durability) lives on the owner of the instance.
- Meshes, materials, sounds and effects in a content asset are soft references in an asset bundle (`Visuals`, later `Audio`), loaded with the asset when it's needed.
- **Data validation:** each content class overrides `IsDataValid` to check its ID format and required fields, so mistakes show up in the editor (right-click > Asset Actions > Validate Assets) instead of at play time.
- When the game needs global data at startup (lists of starting items, default settings), `UVestigeAssetManager`, the project's Asset Manager (`AssetManagerClassName` in `Config/DefaultEngine.ini`), loads it once, as `ULyraAssetManager` does, rather than having each system load its own.

**Pitfalls:**

- Hard references from one data asset to another (`TObjectPtr<UFarmCropData>` inside an item) load the whole chain. Refer to other content by primary asset ID or soft reference.
- Forgetting to register a new type in the Asset Manager settings: the assets exist but the game never finds them, and they aren't cooked.

**The content catalogue** (design for [CodeReview.md, M5](../CodeReview.md#m5--every-inventory-loads-and-keeps-every-item-definition), 2026-11-08, approved after two rounds of review by a senior Unreal C++ reviewer agent, whose approval counts as David's; built the same day as described). Until then four places load content on their own. The inventory component loads every item definition at `BeginPlay` and keeps its own map, so a chest, the shipping bin or a robot's inventory would each do it again. The farming component loads every tool and crop with their `Visuals` bundles at `BeginPlay`, once per pawn, into maps of its own. The field subsystem loads each crop a save names with `UVestigeContentData::LoadWithVisuals`, and so does the `BenchmarkField` command. After this change one game-instance subsystem, the content catalogue, loads every content definition once per game and every system looks content up there; nothing else loads a definition. The catalogue loads only the `Visuals` bundle, so item icons, which come with the hotbar row, go in an `Icons` bundle of their own that a UI loads while it shows them (the rule is below; the icon and its loading are designed with that row).

References: Epic's "Asset Management" page and, checked in the 5.8 source (`AssetManager.h`, `AssetManager.cpp`, `StreamableManager.cpp`): `UAssetManager::LoadPrimaryAssets`, which sets the one bundle state the Asset Manager keeps per primary asset, so a later load or `ChangeBundleStateForPrimaryAssets` of the same assets with other bundles replaces it; `UAssetManager::PreloadPrimaryAssets`, which returns a handle the caller must keep, isn't touched by bundle state changes, and frees what it loaded once no handle holds it; `GetPrimaryAssetTypeInfoList` (each type's `AssetBaseClassLoaded`) and `GetPrimaryAssetObject`, which finds an asset in memory however it was loaded; and `FStreamableHandle`, whose completion callback runs `s.StreamableDelegateDelayFrames` (1) frames after the load ends. Lyra: `ULyraAssetManager` loads its global game data once at startup (our `UVestigeGameData` already does), but its `GetAsset` loads synchronously on first use during play; its experiences load bundles with `ChangeBundleStateForPrimaryAssets`; and `UInventoryFragment_QuickBarIcon` holds its icon as an `FSlateBrush`, a hard reference that loads every icon with its item.

What we take from Lyra and what we skip:

- **Take:** one owner that loads content at a known moment and keeps it for as long as it is needed; bundles to split what loads with a definition from what loads later.
- **Skip:** loading on first use during play (`GetAsset`); icons as hard references in a fragment; bundle state driven by experiences, which we don't have. The catalogue is a game-instance subsystem, not part of the Asset Manager, so it is built again for each game: each Play in Editor session finds the assets made in the editor since the last one, frees what it loaded when the session ends, and each test's game instance has its own.

| Part | Kind | Owns |
| --- | --- | --- |
| `UVestigeContentCatalog` | Game-instance subsystem (`Content/`), new, reached with `Get(World)` | Every content definition, by primary asset ID, loaded in `Initialize` with the `Visuals` bundle and kept until `Deinitialize`; finding a definition (`Find`, `Find<T>`) |
| `UVestigeContentData` | Data asset base (`Content/`) | Loses `LoadWithVisuals` |
| `UVestigeInventoryComponent` | Component on the player state (`Inventory/`) | Loses `LoadItems` and its `Items` map: it finds items in the catalogue |
| `UFarmingComponent` | Component on the pawn (`Farming/`) | Loses `LoadToolsAndCrops`, its `Tools` and `Crops` maps, `FindCrop` and its two test hooks: it finds tools in the catalogue |
| `UFarmFieldSubsystem`, `UFarmGameplayAbility_Plant`, `UVestigeCheatManager` | (`Farming/`, `Player/`) | Find the crops a save, a seed or `BenchmarkField` names in the catalogue instead of loading them |

How it works:

- **When it loads.** In the catalogue's `Initialize`: in a packaged game when the game instance starts, before the first map loads; in the editor when Play in Editor starts; in a test when the fixture calls `InitializeGameSubsystems`. No world plays yet, so waiting for the load is allowed there ([CodingGuidelines.md, section 12.4](../CodingGuidelines.md#124-assets-and-loading)). In every case the game instance's subsystems initialise before its first world is initialised (`UGameInstance::InitializeForPlayInEditor` calls `Init` before `PostCreatePIEWorld`), so the catalogue is full before the save subsystem reads the save. `UFarmFieldSubsystem` still declares it with `Collection.InitializeDependency<UVestigeContentCatalog>()`, because restoring a save reads crops from it, so the order is written down rather than assumed.
- **A finished asset scan first.** `Initialize` checks `UAssetManager::Get().HasInitialScanCompleted()`; if the scan hasn't finished (the editor can defer it until the asset registry has loaded), it logs an error, since an empty catalogue would otherwise look like a game without content.
- **What it loads.** Every primary asset type whose base class (`AssetBaseClassLoaded`) is a `UVestigeContentData` subclass and that is neither a Blueprint-class type (`bHasBlueprintClasses`, whose primary assets are classes) nor editor-only (`bIsEditorOnly`): `FarmCrop`, `VestigeTool` and `VestigeItem` today, not `VestigeGameData` or the engine's types, and a mod's content type later through the same Asset Manager settings, with no code change. It gathers every ID of those types and makes one `PreloadPrimaryAssets(Ids, {Visuals}, false)` call with one `WaitUntilComplete`, which loads the crops' growth meshes and the tools' held meshes with their definitions. It keeps each loaded definition in a `TMap<FPrimaryAssetId, TObjectPtr<const UVestigeContentData>>` (a `UPROPERTY`), and logs how many it loaded and, as a warning, every ID that didn't load. With no content IDs at all it makes no load call, since a preload of nothing returns no handle and fails an `ensure`.
- **Why preload.** A preload handle belongs to the catalogue alone: each game instance owns its load, which ends with that game, and nothing is left in the Asset Manager's process-wide bundle state across Play in Editor sessions or tests. `Deinitialize` calls `ReleaseHandle()` on it (resetting the pointer alone would leave it active while any copy lives) and empties the map, and the Asset Manager frees what no other handle holds. Two game instances at once (Play in Editor with two clients) each hold their own handle. It also keeps the meshes out of the Asset Manager's one bundle state per asset, which any later `LoadPrimaryAssets` of the same assets would replace.
- **Finding.** `Find(Id)` returns the definition or nullptr, and `Find<T>(Id)` casts it, so `Find<UVestigeToolData>` with an item's ID is nullptr. It is a map find and never loads. A missing ID is the caller's warning, as today ("No item has the ID ..."), since only the caller knows what named it.
- **Reaching it.** `UVestigeContentCatalog::Get(const UWorld*)` returns the world's game instance's catalogue, or nullptr when the world has none (an editor preview world). Components ask for it when they look something up, which happens on a player action or a hand change, never per frame; they keep no pointer, so a component made by a test without `BeginPlay` works too.
- **The rule for icons.** The catalogue loads `Visuals` only, which is what the world draws. An item's icon, when the hotbar row in [4.6](../Roadmap.md#46-interface-and-input) adds it, is a soft texture in a bundle of its own, `Icons`, never in `Visuals`, and the UI that shows it preloads it with a handle that UI owns and releases, so icons are in memory only while something shows them and nothing loads them at play start. That row designs the icon property and its loading (an empty or unknown list of items, which gives no handle; icons already in memory, whose callback still comes a frame later; a callback for a handle the UI has replaced), with a caller to test them against.
- **The callers.** The inventory's `FindItem` asks the catalogue for a `UVestigeItemData`; its `BeginPlay` no longer loads, so it registers with the save registry at once. The farming component's `GetCurrentTool` and `GetHarvestTool` ask it for a `UVestigeToolData`. The warnings loading gave stay: `BeginPlay` still warns when `HarvestToolId` names no tool the catalogue has (skipped without a catalogue), and `Grant` warns, with the tool as the log's context object since it is static, when a tool names no ability. The plant ability asks it for the seed's crop. The field subsystem finds the crops a save's tiles name there instead of loading each one (`FindSavedCrops`), and `BenchmarkField` finds its crop there. `LoadWithVisuals` is deleted, as nothing calls it.
- **Layers.** The catalogue sits in `Content/` and knows only the content base class; every user is above `Content/`. No new folder or direction ([Architecture.md, section 14](../Architecture.md#14-dependencies)).
- **Performance.** No tick. One batched load with one wait per game, against one per pawn for the tools and crops, one per inventory for the items and one per crop of a save today. What stays in memory is unchanged: every definition and the crops' and tools' meshes, for the whole game. A lookup is the game instance's subsystem lookup and one map find, on a player action. `Initialize` has a `TRACE_CPUPROFILER_EVENT_SCOPE`. Every test fixture that calls `InitializeGameSubsystems` now loads all content with it; that is a few assets today, and the commit records the time of the whole test run before and after. If content grows to where loading every crop's meshes at start costs too much, the roadmap item that loads only the crops of the seeds the player carries applies here instead, with a measurement first.

Not in this change (into [Roadmap.md](../Roadmap.md)):

- Content added while a game runs (a mod's game feature plugin turned on mid-game): the catalogue sees it at the next game. It listens for new primary assets when mod support is designed.
- The item icon (a soft texture on `UVestigeItemData` in the `Icons` bundle), loading it for a UI, an icon on each item and showing it: with the hotbar row (4.6), by the rule above.
- A loading screen that waits on the catalogue: there is no loading screen yet ([section 20](20-MapsAndMenus.md)), and the catalogue is loaded before the first map, so there is nothing to wait for today.

Tests (`Source/Vestige/Tests/`), each with a fixture that calls `InitializeGameSubsystems`, except the two without a catalogue, which use a local `FActorTestSpawner` that doesn't:

- `Vestige.ContentCatalog.KnowsEveryContentAsset`: every ID the Asset Manager lists for `FarmCrop`, `VestigeTool` and `VestigeItem` is found, as its own class, and the game data (`VestigeGameData:DA_GameData`'s ID) isn't.
- `Vestige.ContentCatalog.LoadsTheVisualsOfCropsAndTools`: every path in each crop's and tool's `Visuals` bundle entry (`GetAssetBundleEntry`) is among the catalogue handle's requested assets (a test hook returns `GetRequestedAssets`), since being in memory alone passes in the editor anyway.
- `Vestige.ContentCatalog.FindsOnlyTheAskedClass`: `Find<UVestigeToolData>` finds `VestigeTool:Base.Hoe` and not `VestigeItem:Base.Hoe`; `Find<UVestigeItemData>` the other way round; an unknown ID finds nothing.
- `Vestige.ContentCatalog.TestContentStaysInItsGame`: `AddForTests` adds a transient item and replaces a real one by ID, and a second test world's catalogue has neither; content without a valid ID is refused.
- `Vestige.ContentCatalog.ShuttingDownReleasesTheLoad`: after the game instance shuts down, the catalogue's handle, kept by the test through the hook, is no longer active (`!IsActive()`) and the catalogue finds nothing.
- `Vestige.Inventory.InventoriesShareTheCatalogue`: two inventory components on two actors find the same `VestigeItem:Base.Turnip` definition, the catalogue's.
- `Vestige.Inventory.WithoutACatalogueNoItemIsKnown` and `Vestige.Farming.WithoutACatalogueNoToolIsInHand`: in a test world without a game instance, adding an item fails and `GetCurrentTool` is nullptr, without a crash. The spawner shuts its game instance down before it destroys its actors, so the components' `EndPlay` meets no catalogue too.
- `Vestige.FarmFields.ASavedCropIsFoundInTheCatalogue`: restoring a saved field puts the catalogue's crop on its tile, and a tile naming an unknown crop is left out and counted.
- Test content goes through `UVestigeContentCatalog::AddForTests(const UVestigeContentData&)`, which adds or replaces by the content's primary asset ID in that game instance's catalogue only, so it ends with the test. `UVestigeInventoryComponent::ResetForTests` loses its items parameter, and the farming component's `AddCropForTests` and `AddToolForTests` go. The inventory, farming and player character fixtures that use items call `InitializeGameSubsystems` once, in `BEFORE_EACH`, and add their test content to the catalogue; the player character test that called it itself (`UnpossessingReleasesTheUseKey`) stops doing so, since a second call makes a second game instance that is never shut down.
