# 5. Input

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** built as assets bound by tag ([CodeReview.md, H6](../CodeReview.md#h6--input-is-built-in-c-with-hard-coded-keys), 2026-11-07, approved by a senior Unreal C++ reviewer agent after three rounds, whose approval counts as David's). The farming actions are `IA_` assets in `Content/Vestige/Input` with one mapping context, `IMC_Farming`; `DA_InputConfig_Player` (`UVestigeInputConfig`) names the action for each native input tag (`Vestige.Input.*`), and `AVestigePlayerCharacter` binds by tag and adds its contexts while possessed. The template's moving and looking (`IA_Move`, `IA_Look`, `IA_MouseLook`, `IA_Jump`, `IMC_Default`, `IMC_MouseLook`) are still bound by the template base class until it is replaced ([CodeReview.md, M6](../CodeReview.md#m6--the-template-code-is-load-bearing)). Rebinding waits for the settings menu ([section 17](17-Settings.md)). The key hints follow the device used last, told by Common Input (gamepad key hints, 2026-11-08, below).

**References:** Epic's "Enhanced Input" pages (input actions, mapping contexts, triggers, modifiers, player-mappable key settings, user settings); Lyra's `ULyraInputConfig` (a data asset mapping input actions to input tags), `ULyraInputComponent` and `ULyraHeroComponent`, which bind actions by tag to abilities.

**Take, skip, change from Lyra:**

- **Take:** the input config data asset with a list of native actions by tag (`FindNativeInputActionForTag`, with a flag for whether a missing tag is an error); native input tags in C++; the pawn adding its mapping contexts and registering them with the Enhanced Input user settings; player-mappable key settings on each action.
- **Skip:** the second list, ability input actions (abilities activated by input tag). None of our keys goes straight to an ability: E goes to `UFarmingComponent::StartUsingTool`, which first follows the inventory, grants the tool in hand and announces the held key for the walk speed, and then presses the spec's input by handle; F goes to `UVestigeInteractionComponent::Interact`, which activates by ability tag. Ability input tags come when the first key maps straight to an ability with no owner logic in between. Skip the custom input component (`ULyraInputComponent`): a small private function on the character finds each action and binds it, so the input component class stays the engine's. Skip `ClearAllMappings` on possession, which would also drop contexts menus add.
- **Change:** contexts are added in `SetupPlayerInputComponent` (as before) and removed in `UnPossessed`, not added in `NotifyControllerChanged`; the input component is made and set up on each possession by the local controller (`PawnClientRestart`), and adding a context that is already applied only changes its priority, so neither path stacks it.

The assets, all Boolean:

The gamepad layout is provisional: interact will likely move to A when jumping moves with the template's replacement ([Roadmap.md](../Roadmap.md), the M6 item). In each action the keyboard or mouse mapping comes first and the gamepad one second, the order the user settings fill an action's key slots in. `BP_PlayerCharacter` names `DA_InputConfig_Player` and the contexts `IMC_Default` (0), `IMC_MouseLook` (0) and `IMC_Farming` (1), as hard references: they are tiny and needed the moment the pawn is possessed, so nothing loads during play.

Tests: `Vestige.Input.*` (every config entry bound, the use key on `Started` and `Completed` and the template's actions still bound, every function with a keyboard and a gamepad key, no key doing two things across the three contexts, unique mappable names, the config's validation), the hint tests in `Vestige.PlayerCharacter`, and the stepping tests in `Vestige.Inventory`. That contexts don't stack on re-possession is a [PlayTest.md](../PlayTest.md) check (`showdebug enhancedinput`), since the actor test spawner has no local player.

**Gamepad key hints (4.0, built 2026-11-08, approved by a senior Unreal C++ reviewer agent after two rounds, whose approval counts as David's).** The key hints and the interact prompt name the keys of the device the player used last: "X Use tool" and "B Sleep" after a gamepad button, trigger or full stick push, "E Use tool" and "F Sleep" after a key, a mouse button, the mouse wheel or a mouse move.

*References:* Epic's "Common UI" overview and "Common UI quickstart" pages (the input subsystem, the platform input data, the game viewport client); `UCommonInputSubsystem` and `FCommonInputPreprocessor` in the engine's CommonUI plugin (`Plugins/Runtime/CommonUI/Source/CommonInput`); the engine's `UInputDeviceSubsystem` (`GameFramework/InputDeviceSubsystem.h`); Lyra: `ULyraButtonBase::OnInputMethodChanged` and `ULyraBoundActionButton` follow `UCommonInputSubsystem`, and `DefaultGame.ini` writes out Common Input's thrashing protection defaults.

*Take, skip, change:*

- **Take:** Common Input's `UCommonInputSubsystem` (a local player subsystem) as the one source of the last used device. Its Slate input preprocessor sorts each key down, mouse button, mouse move and touch by the key or event itself (`FKey::IsGamepadKey`, touch events), keeps `GetCurrentInputType()` (`ECommonInputType`: `MouseAndKeyboard`, `Gamepad`, `Touch`) and fires `OnInputMethodChangedNative`. Analog events never switch it: a stick switches it only past its virtual button threshold, as a stick direction key. Its preprocessor never consumes game input (only an input type that is blocked, and none is by default). It is what Lyra's widgets follow and what the Common UI widgets of the first menu will follow, so the HUD and the menus can never disagree about the device. Thrashing protection (on by default: more than 30 changes, each within 3 seconds, lock it to keyboard and mouse for 1 second) only stops runaway switching; a bumped mouse still switches the hints back at once, which is right.
- **Skip:** the engine's `UInputDeviceSubsystem` (`GetMostRecentlyUsedHardwareDevice`) as our source: it would work on Windows (each XInput pad gets its own device id with a gamepad descriptor), but it answers which hardware, not which kind of input, and depends on each backend's descriptors and input config; Common Input sorts by the key itself, adds the thrashing protection, already uses `UInputDeviceSubsystem` for its gamepad type detection, and is what the menus will use. Skip writing our own Slate preprocessor: it would be Common Input's preprocessor again. Skip Common UI's widgets, its action router's input routing, `UCommonGameViewportClient`, the platform input data (`UCommonUIInputData`) and the controller data with button icons (`UCommonInputBaseControllerData`): they come with the first menu ([Roadmap.md](../Roadmap.md), Common UI with the first menu), and icons need art. Skip a device per platform user: the game has one local player.
- **Change:** without a `UCommonGameViewportClient`, Common UI's action router (`UCommonUIActionRouterBase`, a local player subsystem created whenever the plugin is on) logs an error at start that its input routing won't work. We use no routing yet, so `CommonUI.Debug.CheckGameViewportClientValid=0` under `[SystemSettings]` in `Config/DefaultEngine.ini` silences the check, as the error itself suggests (the cvar isn't a cheat, so the ini value reaches it when the module registers it). That only silences the log. The router's analog cursor is created on every local player either way, and is registered as an input preprocessor only with a `UCommonGameViewportClient`, so it doesn't move a cursor; but it, and Common Input itself (a faux Slate cursor on gamepad, `CommonInput.EnableGamepadPlatformCursor` off), still hide and restore the cursor on each switch. While playing, the game captures and hides the mouse anyway; the play-test checks the cases around it (below). The first menu sets the viewport client and removes the setting and its test. Gamepad buttons are named in short text ("X", "B", "LB / RB") until the controller data gives icons.

*Classes:*

- **Plugin and module:** `CommonUI` is enabled in `Vestige.uproject` (its `CommonInput` module is the one we use; the plugin also loads the `CommonUI` module), and `CommonInput` joins the private dependencies in `Vestige.Build.cs`. No content or settings of the plugin are set: Windows's platform input data (`DataDrivenPlatformInfo.ini`) already defaults to keyboard and mouse and supports the gamepad. Only `UI/` and the tests include Common Input headers.
- **`Player/VestigeKeyHints.h` and `.cpp`:** `FVestigeKeyHint`, with
   - `enum class EVestigeHintDevice : uint8 { KeyboardAndMouse, Gamepad }`, the device hints are for;
   - `FText VestigeKeyHints::GetKeyName(const FKey& Key)`, the short name a hint shows. Gamepad keys always get the Xbox labels players on Windows expect (`LOCTEXT`, namespace `VestigeKeyHints`): face buttons A, B, X, Y; shoulders LB, RB; triggers LT, RT; stick clicks LS, RS; the special buttons View and Menu; the D-pad "D-pad Up", "D-pad Down", "D-pad Left", "D-pad Right". Every other key is `Key.GetDisplayName(false)`. It doesn't read `EKeys::ConsoleForGamepadLabels`, which the editor sets from a per-user experimental setting. A gamepad's own names (PlayStation's Square, Circle) come with the controller data and its icons.
- **`AVestigePlayerCharacter`:** the three hint functions take `EVestigeHintDevice Device`.
   - `FindHintKey(Action, Device)`: for `Gamepad`, the first mapping of the action in the pawn's contexts whose key is a gamepad key (`IsGamepadKey`); for `KeyboardAndMouse`, neither a gamepad, touch nor gesture key.
   - `GetActionKeyHints(Device)`: the action hints, with the device's key named by `GetKeyName` ("X Use tool", "B Interact").
   - `GetInteractKey(Device)`: the interact key of the device ("B").
   - `GetHotbarKeyHints(Inventory, Device)`: for the keyboard, one hint per non-empty hotbar slot ("1 Hoe"). The gamepad has no slot keys, it steps, so for `Gamepad` it is one hint, the previous and next actions' gamepad keys formatted as `LOCTEXT("HotbarStepKeys", "{Previous} / {Next}")` ("LB / RB") with the action `LOCTEXT("HotbarStepHint", "Hotbar")`, and only when the hotbar has an item and both keys are found. The keys come from the mappings (A-14); the word is ours, as the hint's format already is, and the slot names stay on the status line (the item in hand).
- **`AVestigeHUD`:** follows the device.
   - `static EVestigeHintDevice GetHintDevice(ECommonInputType InputType)` (public): `Gamepad` for `Gamepad`, `KeyboardAndMouse` for the rest; the game has no touch controls, so a touch on a touch-screen laptop leaves the keyboard hints.
   - In `BeginPlay`, after creating the widget and before the first refresh, on the local player path that makes the widget, it finds `UCommonInputSubsystem::Get(PlayerOwner->GetLocalPlayer())` (local player subsystems start in `ULocalPlayer::PlayerAdded`, before the HUD exists), keeps it in a `TWeakObjectPtr`, sets `HintDevice` from `GetCurrentInputType()` and binds `OnInputMethodChangedNative` (a `DECLARE_EVENT`) with `AddUObject` to `HandleInputMethodChanged`. Without a local player there is no widget and nothing to follow; `HintDevice` defaults to `KeyboardAndMouse`.
   - `HandleInputMethodChanged(ECommonInputType NewType)` maps the type and, only when `HintDevice` changes, stores it and calls `RefreshKeyHintsText` and `RefreshPromptText`. The event also fires with an unchanged type (gamepad type detection, the `CommonInput.ShowKeys` cvar) and for a touch after the mouse; those rebuild nothing.
   - `EndPlay` unbinds through the weak pointer (`RemoveAll(this)`). `RefreshKeyHintsText` and `RefreshPromptText` pass `HintDevice` to the character. The hints are built only on events: a device change is one more event, and the lookups never run per frame.

*Tests:* the hint functions for both devices and `GetKeyName`'s short names (`Vestige.PlayerCharacter.*`, `Vestige.Input.GamepadKeysHaveShortHintNames`), and `Vestige.UI.TheHintDeviceFollowsTheInputType`. Two tests guard settings: `Vestige.Input.ThePlatformDefaultsToKeyboardAndMouse` (`UCommonInputPlatformSettings::Get()` must support keyboard and mouse and the gamepad and default to keyboard and mouse; otherwise Common Input ignores the types the platform doesn't support and the hints would be stuck) and `Vestige.Input.TheActionRouterCheckIsOff`, which the first menu removes with the setting. The HUD following the device needs a local player, which the test spawner doesn't have, so it is a play-test check.

**Rules:**

- Input actions (`IA_`) and mapping contexts (`IMC_`) are assets in `Content/Vestige/Input`. Mapping contexts are added and removed by context (on foot, in a menu, driving a machine) with explicit priorities. The pawn owns the contexts of its body (`MappingContexts` on the character); menus will add their own on the player controller. Every context add has a matching remove: the character adds its contexts in `SetupPlayerInputComponent` with `FModifyContextOptions::bNotifyUserSettings` set, so they register with the player's Enhanced Input user settings, and removes them in `UnPossessed` with the default options, so they stay registered for the next possession.
- Code binds by native input tag (`VestigeGameplayTags::Input_*`), never by asset: the character asks its input config for the action of each tag. A missing config logs an error and binds nothing (the contexts are still added); a tag missing from the config logs an error. The config validates in the editor: every entry has an action and a tag under `Vestige.Input`, no tag or action twice, every action is Boolean, and an action with player-mappable settings has a mapping name.
- The character binds input to calls on the components that own the action (`UFarmingComponent::StartUsingTool` on the use key's `Started`, `StopUsingTool` on its `Completed`); input code holds no game rules. Holding a key to repeat an action is the owner's rule, driven by events rather than by `Triggered`, which fires every frame: the press activates the tool's ability with its spec's input pressed, and the ability itself starts the next use when the last one ends or the target tile changes, and only if the use would change the tile, so a held key never posts a message every frame ([section 9](09-AbilitySystem.md), tools as abilities). While it is held the farmer walks and jumps at half speed, a setting on the movement component (`ToolUseSpeedScale`), so a row is worked evenly. No tool works in the air (the tool ability waits for the farmer to walk again while the key is held), and a held key resumes on landing, so jumping can't get round the slower walk. Keys 1 to 9 select the inventory's hotbar slots, through the character's `SelectHotbarSlot`, and the mouse wheel and the gamepad shoulders step through them, through its `StepHotbarSlot`, which forwards to the inventory's `StepHotbarSlot` ([section 8](08-Inventory.md), the hotbar). The character also releases a held use key in `UnPossessed`, before the input component and its release binding are destroyed, so the walk speed is never left halved. E uses the item in hand and nothing else; F interacts with the bed and harvests the ripe tile the farmer faces ([section 7](07-Interaction.md), harvesting with F). Movement input also aims the targeting component, `UFarmTargetingComponent`, at a neighbouring tile (`AimAt`), and the walk eases in from the press, read from the move action's elapsed time (`FInputActionInstance::GetElapsedTime`), so the template's `IA_Move` needs no extra trigger or modifier. Turning belongs to the farmer's movement component, `UVestigeCharacterMovementComponent`, which turns toward the aimed tile when there is no input.
- Keys bind natively to the owner of the action, never to an ability by input tag, while every key goes through owner logic first (the use key, interact). When a key first maps straight to an ability with no owner logic in between, the input config gains Lyra's ability input actions and that ability activates by input tag.
- Key hints on screen come from the mappings, never hard-coded text ([ArchitectureAudit A-14](../ArchitectureAudit.md)). The action hints are every action of the input config with an `ActionDescription`, in the config's order; the hotbar hints are the slot actions' keys on the keyboard and, on the gamepad, which steps, the previous and next keys ("LB / RB Hotbar"). The hints name the keys of the device the player used last (`UCommonInputSubsystem`, followed by `AVestigeHUD`; gamepad key hints, above): a key is the first mapping of the action in the pawn's contexts that is a gamepad key on the gamepad, or neither a gamepad, touch nor gesture key on the keyboard, named by `VestigeKeyHints::GetKeyName` (Xbox labels for gamepad buttons until controller data gives icons). Reading the assets' default mappings is right while keys can't be rebound; with rebinding, the hints ask Enhanced Input for the player's current key and the HUD rebuilds them on a remap event ([Roadmap.md](../Roadmap.md), the settings item). The HUD builds the hints only on events, so the lookups (about fifteen entries, three contexts) never run per frame.
- Player rebinding uses Enhanced Input's player-mappable key settings and its user settings save game ([section 17](17-Settings.md)). Every action has player-mappable key settings whose `Name` is its input tag (`Vestige.Input.UseTool`), one naming scheme, and a display name. The user settings stay off (`bEnableUserSettings`) until the settings menu.
- Gamepad support is designed in from the first asset-based mapping: every function has a gamepad key. The direct slot keys 1 to 9 are keyboard conveniences; the gamepad reaches the same slots by stepping.
- The template's actions have no mappable names and are bound through the template's own properties; they join the input config when the template goes ([CodeReview.md, M6](../CodeReview.md#m6--the-template-code-is-load-bearing)).

**Pitfalls:**

- Adding a mapping context every time a pawn is possessed without removing the old one. Every add has a matching remove.
- Using the legacy input system (`BindAxis`, `BindAction` on `UInputComponent`) in new code.
- Hotbar stepping binds `Started`, so several wheel notches in one frame are one step; fast scrolling can skip fewer slots than notches.
- Renaming a mappable name once players can save remaps: it is the key the remap is saved under ([section 17](17-Settings.md)).
- Common Input hides and restores the cursor on each device switch. After stopping Play in Editor right after using the gamepad, the editor's cursor can stay hidden until the next Play; `CommonInput.EnableGamepadPlatformCursor=1` would stop Common Input swapping it.
