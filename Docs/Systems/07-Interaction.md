# 7. Interaction

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** built (2026-11-01, milestone 2 foundations, [Roadmap 4.1](../Roadmap.md#41-foundations)), approved by David on 2026-11-01 with the option list: `IVestigeInteractable`, `UVestigeInteractionComponent` on the player's pawn, the interact ability, the F key and the HUD prompt. The interactables are the bed, one placed in `L_Farm`, and the farm grid, for harvesting a ripe tile with F (2026-11-07, below).

**References:** Epic's "Interfaces" page (`UINTERFACE`, `BlueprintNativeEvent` functions called through `Execute_`, `Implements<U...>()`), "Collision Overview" and "Collision Response Reference" (custom object channels and collision profiles in Project Settings > Collision), and `UWorld::OverlapMultiByObjectType`. Lyra's interaction (`Source/LyraGame/Interaction`): `IInteractableTarget` fills an `FInteractionOption` list (text, sub-text, the ability to run and the target's own ability system), `UAbilityTask_GrantNearbyInteraction` runs an overlap query around the player on a timer (every 0.1 s) on Lyra's interaction channel, `UAbilityTask_WaitForInteractableTargets_SingleLineTrace` picks the one the camera looks at, and `ULyraGameplayAbility_Interact` shows the prompt and activates the option's ability, which receives the target in its event data.

**What we take from Lyra and what we skip:**

- **Take:** one interface every usable thing implements; the option list, so an object can offer several actions without the interface (a mod API) changing when the first one does; a cheap overlap query around the player on a timer, on a dedicated collision channel; using it as a gameplay ability, so tags can block it later (in a menu, in dialogue).
- **Skip:** granting each target's ability to the player and running the option's ability (Lyra's `InteractionAbilityToGrant`): the interactable does the action itself. That machinery exists for networked play, where the server must run the ability.
- **Until there is a way to choose** (a menu, or a key per option), the interact key uses the first option (decided with David, 2026-11-01). An interactable lists its options with the one the player most likely wants first.
- **Skip:** the camera line trace. Our camera is a third-person follow camera over a farm, so the farmer's aim, not the camera, says what he means: the focus is the nearest interactable he faces (harvesting with F, below).

**Rules:**

- **One interface, `IVestigeInteractable`** (`UINTERFACE(Blueprintable)`), so C++ actors and Blueprint actors (and so mods) can both be interactable. Two `BlueprintNativeEvent` functions, called through `IVestigeInteractable::Execute_...`:
   - `GetInteractionOptions(Interactor, OutOptions)`: fills `OutOptions` with what can be done with it now, each an `FVestigeInteractionOption` (`BlueprintType` struct): `Text`, the prompt's verb (`Sleep`), and `Action`, an `FName` the interactable chooses to tell its own options apart (`Sleep`). No options means there is nothing to do right now, and the actor isn't offered. It must be cheap and change nothing: it is asked on every scan. Later fields (a second line, an icon) are added to the struct without changing the function.
   - `Interact(Interactor, Option)`: does the chosen option. The interactable owns what happens and asks the interactor's own components for anything about the player (the bed asks the interactor's `UVestigeRestComponent`, found on its player state with `UVestigeRestComponent::Find`, to `Sleep`). The interactor never knows the interactable's class: no `if` per class.
   - Both are extension points ([Architecture.md, section 12](../Architecture.md#extension-points-today)) and listed in `Vestige.ExtensionPoints.*`.
- **Interactables are found by collision, not by class.** A new object channel, `Interactable` (default response Ignore, so nothing else notices it), and a collision profile `VestigeInteractable` (object type `Interactable`, queries only, ignoring every channel: a query by object type finds it without a response) for the shape that marks where an actor can be used from: a box component a little bigger than the bed. The actor's own blocking collision stays as it is.
- **`UVestigeInteractionComponent` on the player's pawn owns finding and using interactables.** Every `ScanSeconds` (0.2 s) a timer runs one `OverlapMultiByObjectType` for `Interactable` in a sphere of `InteractionRadius` (100 cm, one tile) around the pawn, keeps the overlapping actors that implement the interface and offer at least one option the pawn faces, and focuses the nearest of those (harvesting with F, below). It gathers the options into one array it reuses, so a scan allocates nothing once warmed up. It keeps the focus as a weak pointer with its first option, keeps the latest option (its location can change while its prompt stays), and broadcasts `OnFocusChanged` only when the focused actor or that option's action or text changes. No tick; the timer stops at `EndPlay`.
- **Interacting is a gameplay ability**, `UVestigeGameplayAbility_Interact`, granted by `DA_AbilitySet_Player` and activated by its asset tag `Vestige.Ability.Interact` (a native tag). The interaction component's `Interact` activates it; the ability asks the component to rescan once (so the focus is current, not up to 0.2 s old) and calls `Interact` on the focus with its first option, then ends. It is instanced per actor, has no cost and takes no time today; an interaction that takes time later (filling the watering can) holds it active as a tool ability does.
- **Input: F interacts** (`Interact`, an input action the character maps and binds to the interaction component, shown in the key hints like the others), and F also harvests the ripe tile the farmer faces (below). E only uses the item in hand, so a tile next to the bed can still be hoed. **The bed is how the player sleeps.** Sleeping is instant: it starts the next day at 06:00, so there is no sleeping state and nothing to wake from. A day nobody sleeps through ends at 06:00 the next morning. Skipping to the next day anywhere is the `SkipDay` console command ([section 19](19-DebuggingAndCheats.md)).
- **The prompt on the HUD** is presentation: `AVestigeHUD` listens to `OnFocusChanged` on the possessed pawn's interaction component and shows "F Sleep" (the interact key, read from the mapping context like the other key hints, and the first option's text) while something is focused. Nothing is drawn in the world yet; an outline or a marker over the focused actor is a later presentation component.
- **The bed, `AVestigeBed`** (in `Farming/`, next to the rest component it asks): a static mesh with blocking collision (an engine cube set in C++ as a placeholder until the bed mesh in [Roadmap 4.6](../Roadmap.md#46-interface-and-input)) and the interaction box. It offers one option, `Sleep`, whenever the interactor has a rest component, and interacting with it calls that component's `Sleep`, so the rules of sleeping (the refill, bedtime and exhaustion) stay with the rest component. `BP_Bed` in `Content/Vestige/Blueprints` is the bed levels place and will hold the real mesh; one lies along the near edge of the field in `L_Farm`, so a tile can be worked from beside it, until there is a farmhouse.
- **Layers:** the interface, the interaction component and the ability need nothing above `AbilitySystem/`, and everything usable (the bed in `Farming/`, the shipping bin, robots) sits above them, so they get a layer folder of their own, `Interaction/`, right above `AbilitySystem/`. The tag joins `AbilitySystem/VestigeGameplayTags`.
- **Saving:** nothing. The focus is recomputed, and an interactable that has state (a chest) saves it as its own owner ([section 1](01-Saving.md)).
- **Performance:** one overlap query on a channel only interactables use, five times a second, and a loop over the few actors it returns, with one ray against one shape for each whose option has no location (the bed); no world search, no allocation once the options array has grown, no strings rebuilt unless the focused option changed, no tick.
- **Tests** (`Vestige.Interaction.*`): focusing, the focus event, interacting with the first option, the ability by its tag, and the bed (`Vestige.Interaction.TheBed...`). The ability test uses `BP_PlayerState`, so it also fails if `DA_AbilitySet_Player` doesn't grant the interact ability, and a test checks the channel and profile in `DefaultEngine.ini`. The interface functions are listed in `Vestige.ExtensionPoints`.

**Harvesting with F** (2026-11-07, decided with David after the hotbar play-test, approved by a senior Unreal C++ reviewer agent after three rounds of review, whose approval counts as David's). **F interacts with things in the world, and a ripe crop is one of them. E only uses the item in hand, and an empty hand isn't a tool.** Facing a ripe crop shows "F Harvest", the way the bed shows "F Sleep".

References: the interaction design above; Lyra's `IInteractableTarget::GatherInteractionOptions` and `FInteractionOption` (an option names its target object, `InteractableTarget`, so one actor can offer options about something else), and `UAbilityTask_WaitForInteractableTargets_SingleLineTrace`, which picks the target the player faces. The tool abilities and their grant: [section 9](09-AbilitySystem.md), tools as abilities. Engine behaviour below was checked in the 5.8 source.

How it works:

- **The parts.** `FVestigeInteractionOption` has `bHasLocation` and `Location`: where in the world the option is, when that isn't its actor's location (a tile of a large actor); they were added to the struct, so the interface functions didn't change. `UVestigeInteractionComponent` focuses by facing (below), with the facing direction from a delegate its owner binds (`FacingDirection`), else the owner's forward vector. `AFarmGrid` implements `IVestigeInteractable`, with an `InteractionVolume` box over the field and one tile around it, and offers "Harvest" while the interactor faces a ripe tile of this grid. `UFarmingComponent::HarvestToolId` (`VestigeTool:Base.Hand`) names the harvest's data, `DA_Tool_Hand` (the harvest ability `UFarmGameplayAbility_Harvest`, cost 1, use time 0.4 s), whose ability is granted all the time, apart from the tool in hand, and `Harvest()` activates it once; it is in nobody's hand. `AVestigePlayerCharacter` binds the interaction component's `FacingDirection` to the targeting component's `GetAimDirection`.
- **The option.** `AFarmGrid::GetInteractionOptions(Interactor)` finds the interactor's `UFarmTargetingComponent`; if its grid is this grid and its target tile holds a ripe crop (`FFarmTileState::IsRipe`), it adds `{Text "Harvest", Action "Harvest", bHasLocation true, Location the tile's centre (GetTileTransform)}`; otherwise nothing. That is a component lookup and a tile read, five times a second while the farmer is near the field, with no allocation (the options array is the scan's, reused). The scan adds one ray against one shape for each candidate whose option has no location (the bed, when near it). The prompt follows the focus as for the bed.
- **Where it can be used from.** `InteractionVolume`, a box with its own extents: in X and Y the field plus one tile on every side, so a farmer standing just off the field and facing in is found; in Z from 50 cm below the grid to 200 cm above it, so the scan's sphere (100 cm around the capsule's centre, about 96 cm above the feet) overlaps it on uneven ground and mid-jump, as the bed's volume has a height of its own (`InteractionExtent`, `InteractionLocation`). Its collision is set in the constructor: the `VestigeInteractable` profile (which ignores `Pawn`, so it doesn't affect navigation), overlap events off and `SetCanEverAffectNavigation(false)`. `UpdateBounds` sizes it with `Bounds`, and `BeginPlay` calls `UpdateBounds` too, since `OnConstruction` doesn't run in a cooked game for a grid saved in a level before the box existed (`L_Farm`'s).
- **Facing.** The scan asks, for each candidate's first option, whether the pawn faces it, and focuses the nearest faced one, so next to the bed F doesn't sleep (instant, and it ends the day) when the player meant to harvest:
   1. **An option with a location** (`bHasLocation`, the crop) is faced when its location is within `FrontHalfAngleDegrees` (50) of the facing direction on the ground plane, or within 1 cm of the pawn. Its distance is to that location.
   2. **An option without a location** (the bed) is faced only when the facing ray hits the shape the scan found: `Overlap.GetComponent()->LineTraceComponent(...)` from the pawn along the facing direction, `2 * InteractionRadius` long, at the height of the shape's centre (`Bounds.Origin.Z`) so any shape height works. In 5.8 `UPrimitiveComponent::LineTraceComponent` traces that one body directly, with no channel filter, so the query-only `VestigeInteractable` profile is hit; it is one ray against one shape, with no world query and no allocation. Its distance is to the hit point. A ray that starts inside a shape isn't relied on (the farmer's capsule, 42 cm in radius, can't bring his centre inside the bed's box, which is 20 cm larger than the bed).
   3. **Among faced options the nearer wins.** Not the smallest angle: a ray-faced bed has an angle near 0 and would beat a ripe crop standing between the farmer and the bed.

   Why the bed needs the ray: the bed (200 by 100 cm, its box 120 by 70 cm half-extents) lies along the field edge, and a farmer on the edge row has its centre about 92 cm to his side. Aiming along the edge with the bed's centre d cm ahead, its angle is atan(92 / d), under 50 degrees once d passes about 77 cm, while the scan still finds its box up to d of about 217 cm: beside the bed's foot half and up to a metre past it, an angle test would focus the bed (43 degrees at d = 100, 31.5 at d = 150) and F with an unripe target would sleep. Along the edge the facing ray passes 92 cm from the bed's centre, outside its 70 cm half-width, and misses; facing the bed's long side anywhere, or its end from the ring of tiles around the field, hits. Narrowing the cone wouldn't do: facing the bed's long side near one end, its centre is about 47 degrees off.

   The facing direction is the aim, not the actor's rotation: `FacingDirection` is a delegate returning a ground direction, which `AVestigePlayerCharacter` binds to `UFarmTargetingComponent::GetAimDirection` in `BeginPlay` and unbinds in `EndPlay`, and which falls back to the owner's forward vector when unbound or zero (other pawns). The aim is snapped to eight directions, and while walking the actor faces the raw movement direction, up to 22.5 degrees away, so the actor's rotation would put the target tile up to about 67.5 degrees off; measured from the aim, the target tile's centre is at most 45 degrees off for an orthogonal aim (the farmer at a corner of his tile) and about 27 degrees for a diagonal one, inside 50. The aim is snapped to the grid's eight directions everywhere in the level, so near an interactable away from the field the facing used can be up to 22.5 degrees off the farmer's visible facing while he walks; he turns to the aim when he stops, which is enough for the bed and for interactables to come, but a future interactable that needs finer facing should know it. An actor whose first option isn't faced is skipped, as an actor without options is.
- **The focused option stays current.** `SetFocus` always copies the new option into `FocusedOption` and broadcasts `OnFocusChanged` only when the actor or `IsSameAs` (action and text) changes, so moving from one ripe tile to the next updates the option's `Location` without redrawing the prompt. `InteractWithFocus` rescans once after `Execute_Interact`, so the prompt clears as soon as the harvest is done instead of up to 0.2 s later.
- **Interacting.** `AFarmGrid::Interact(Interactor, Option)` does nothing unless `Option.Action` is `Harvest` (as the bed checks its `SleepAction`); then it calls the interactor's `UFarmingComponent::Harvest()`. `Harvest()` calls `FollowInventory()` first, as `UseTool` does (it also keeps the harvest grant current), then activates the harvest spec by its handle without pressing its input. Its input is never pressed, so `IsKeyHeld()` is false and the ability does one use: it reads the target tile from the targeting component, harvests (or says "No room in your bag."), commits the cost, reports `On Crop Harvested` and `On Tool Used` (with `DA_Tool_Hand` as the tool), and stays active for the use time, then ends. It runs inside the interact ability's activation, which is allowed: `InternalTryActivateAbility`'s `ABILITYLIST_SCOPE_LOCK` only defers adding and removing specs, and the harvest spec already exists; the interact ability's `CommitAbility` has no cost or cooldown. While a tool ability is active, `Vestige.State.UsingTool` blocks the harvest: during a use's time, and also while a tool ability waits idly with E held. Then F does nothing although the prompt says "F Harvest"; the interact ability still ends. F isn't held to repeat; harvesting a row by holding F is a later item.
- **E with nothing to use.** `GetCurrentTool()` returns the item in hand's tool, or nullptr for an empty slot, an item without a tool fragment, or a tool that isn't loaded. `StartUsingTool` marks the key held (the slower walk) only when there is a tool in hand; with none and an inventory reachable, it says "Nothing in hand to use." on the press, and logs the missing-tool warning on the press when the item names a tool that isn't loaded (the hand-change event can't, since an empty slot and such an item are both nullptr). A press whose tool's grant is still queued finds no spec and does nothing quietly. The HUD's status line says "Empty hand" or the item's name.
- **The two grants.** The harvest grant has its own state, `HarvestSpec` and `HarvestAbilitySystem` (weak), apart from the tool grant's `GrantedSpec`, `GrantedAbilitySystem` and `GrantedTool`, since the tool grant's state empties whenever the hand does. `UpdateGrantedTool` first updates the harvest grant (when the reached ability system differs from `HarvestAbilitySystem`: release the old, give the new with `DA_Tool_Hand` as the source object), then the tool grant. `ReleaseGrant(FGameplayAbilitySpecHandle&, TWeakObjectPtr<UAbilitySystemComponent>&)` releases either: an active spec is released and removed when it ends, otherwise `ClearAbility`, then the handle and pointer are reset. `EndPlay` and an ability system change release both. Selecting slots never touches the harvest grant. A pawn that reaches an ability system has the harvest granted, plus the tool's when the item in hand is a tool. [CodingGuidelines.md, section 12.3](../CodingGuidelines.md#123-memory-and-allocation)'s grant exception covers the harvest's one ability object per possession.
- **The rename.** `DefaultEngine.ini` has `+PropertyRedirects=(OldName="/Script/Vestige.FarmingComponent.HandToolId",NewName="/Script/Vestige.FarmingComponent.HarvestToolId")` under `[CoreRedirects]`, for values saved under the old name. A test checks the Blueprint's `HarvestToolId`.
- **Layers.** `AFarmGrid` (`Farming/`) implements an `Interaction/` interface and asks `Farming/` components; the character wires the targeting component into the interaction component. The interaction component knows no farming.
- **Saving:** nothing.

**Pitfalls:**

- One `if` per interactable class in the farmer's code: the reason the interface exists.
- Calling an interface function directly (`Cast<IVestigeInteractable>(Actor)->Interact(...)`): a Blueprint that implements the interface has no C++ interface behind it, so the cast returns null and the Blueprint is never asked. Always call `IVestigeInteractable::Execute_Interact(Actor, ...)` and test with `Actor->Implements<UVestigeInteractable>()`.
- Interactables on the `Visibility` or `Pawn` channels, or a scan with `OverlapMultiByChannel` on a shared channel: every query would also return the farm tiles and other actors. Keep the dedicated object channel.
- An options function with side effects or a load: it runs five times a second while the player is near.
