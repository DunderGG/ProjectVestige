# 22. Farm fields and tiles

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** the data is built: `UFarmFieldSubsystem` keeps one `UFarmField` per field ID, each a row-by-row array of `FFarmTileState` with the farming rules (2026-11-04, [CodeReview.md, C1](../CodeReview.md#c1--all-game-state-lives-in-the-level-but-the-game-needs-several-maps)). Drawing with instanced meshes is built as designed below (2026-11-05, [Roadmap.md, 4.0](../Roadmap.md#40-structure-from-the-code-review), [CodeReview.md, C2](../CodeReview.md#c2--one-actor-per-tile-each-with-two-meshes-and-two-dynamic-materials)), approved by @DunderGG on 2026-11-05. A crop's growth stages, a small size step each night it grew, and a ripe mesh of its own are built for the first crops of [4.2](../Roadmap.md#42-farming-depth) (2026-11-13, below). Seeds and the season (refusing out-of-season seeds, asking before a planting too late, the days to ripen on the HUD) are built (2026-11-19, below, the rule "Seeds go in only in their seasons"). A water level on each tile ([Roadmap.md, 4.2](../Roadmap.md#42-farming-depth)) is built as designed below (2026-11-20, the rule "Each tile holds a water level"), on the recommended options of [GameDesign.md, section 15](../GameDesign.md#15-open-questions) until @DunderGG answers them. Radiation per tile and placing objects on the grid ([section 16](16-PlacingAndBuilding.md)) build on it.

**References:**

- Epic's "Instanced Static Mesh Component" page and the `UInstancedStaticMeshComponent` class reference: many copies of one mesh drawn as one primitive, each instance with its own transform and, optionally, a few floats of per-instance custom data.
- Epic's "Nanite Virtualized Geometry" page: Nanite draws every instance of an instanced component through the GPU scene and culls each instance there. The hierarchical variant (`UHierarchicalInstancedStaticMeshComponent`) adds CPU-side culling and LODs for meshes without Nanite, so Nanite art doesn't need it.
- The material nodes **PerInstanceCustomData** and **PerInstanceCustomData3Vector**: a material reads an instance's custom data floats, which replaces a dynamic material per object. A material drawn on instances needs **Used with Instanced Static Meshes** ticked and saved; UE 5.8 doesn't set missing usage flags during play, and such a material draws the grey default material instead.
- The engine source, `Components/InstancedStaticMeshComponent.h` in 5.8: `AddInstanceById`, `RemoveInstanceById`, `UpdateInstanceTransformById` and `SetCustomDataById` name an instance by an `FPrimitiveInstanceId`, which stays the same when other instances are removed. An instance's index doesn't: removing one moves the others.
- Lyra has nothing like a tile grid. We take only its general rule that data and presentation are separate objects.

**How the parts fit:**

| Part | Kind | Owns |
| --- | --- | --- |
| `UFarmField` + `FFarmTileState` | Object in `UFarmFieldSubsystem`, struct per tile | The tiles as data (each tile's water level included), the rules, the field's copy of the water numbers (`FFarmWaterRules`), and the events `OnTileChanged` (one tile) and `OnTilesChanged` (many at once) |
| `UFarmFieldSettings` | Developer settings (Project Settings > Game > Vestige Farm Fields, `Config/DefaultGame.ini`) | The water numbers every new field starts with: the cap, the steps one watering adds and the nightly fall |
| `AFarmGrid` | Actor placed in the level, as `BP_FarmGrid` | Where its field lies (the actor's corner, `TileSize`), finding its field by `FieldId`, converting between world space and coordinates, a tile's transform in the world (`GetTileTransform`), `OnFieldReady` once it has its field, resizing for developer tools. The interactable for its tiles: offering Harvest while the interactor faces a ripe tile, from `InteractionVolume` over the field and one tile around ([section 7](07-Interaction.md), harvesting with F). No tile actors and no drawing |
| `UFarmFieldMeshesComponent` | Scene component on the grid | Drawing the grid's field: one instanced static mesh component per instance set, one soil instance and at most one crop instance per tile, kept up to date from the field's events. Presentation only |
| `FarmTileLooks::GetLook` | Pure function (`FarmTileLooks.h`) | What one tile looks like: for its soil and its crop, the mesh, material override, transform in the grid and colour, from the tile's state and the meshes component's settings. Tested without a world |

**Rules:**

- **Tiles are data, not actors.** Nothing spawns an actor or creates a `UObject` per tile. Game code names a tile by its field and its coordinates (column X, row Y) and asks the field to change it. Something on the grid becomes an actor only when it needs to be one, such as a placed sprinkler with behaviour ([section 16](16-PlacingAndBuilding.md)).
- **One instanced static mesh component per instance set.** A set is one mesh with one material override (none means the mesh's own materials): tilled soil (dry or wet, one set), each crop growth stage mesh, and the placeholders (grass among them). The meshes component creates a set's component the first time a tile needs it and keeps it until the grid ends; a set's mesh never changes. A tile whose look changes moves its instance to another set.
- **Per-tile numbers are per-instance custom data, never a dynamic material.** Every set has the same custom data layout, so a material reads the same index on every mesh:

  | Index | Holds | Read by |
  | --- | --- | --- |
  | 0 to 2 | Colour (linear RGB) | `M_FarmPlaceholder`, the placeholder shapes' material. The Blender art ignores it |
  | 3 | The tile's wetness, 0 (dry) to 1 (at the cap): `WaterLevel / MaxLevel` (`FarmTileLooks::WaterCustomDataIndex`), on the soil and on the crop | `M_FarmSoil`, the tilled soil's material. `M_Crop` may read it for a thirsty look later |
  | 4 and up | Free, for radiation next | |

  `FarmTileLooks::NumCustomDataFloats` is 4. The meshes component sets `NumCustomDataFloats` when it creates a set's component, before it adds an instance.
- **The soil's wetness is custom data on one soil set,** never a set or a material of its own ([GameDesign.md, section 15](../GameDesign.md#15-open-questions), how the player sees a tile's water):
   - `FarmTileLooks::GetLook(const FFarmTileState& Tile, const FFarmTileLookSettings& Settings, int32 MaxWaterLevel)` sets `FFarmTilePartLook::Water` (0 to 1, the tile's level over `MaxWaterLevel`, at least 1) on the soil and on the crop part; the meshes component passes its field's `GetWaterRules().MaxLevel` and writes the value to custom data 3. A fraction, not the level, so a changed cap needs no material change. The crop carries it too, so the thirsty crop look (a follow-up item) can read it in `M_Crop` with no code change.
   - **The art:** `SM_Soil_Tilled`'s material slot holds `MI_FarmSoil_Tilled`, an instance of the project material `M_FarmSoil` (Used with Instanced Static Meshes saved), which reads custom data 3 (a **PerInstanceCustomData** node, index 3, default 0) and moves from its dry to its wet values: `DryColor` to `WetColor` (darker, the same hue) and `DryRoughness` to `WetRoughness` (lower), so each step at the cap of 2 is one step darker and a little glossier. A difference in value, not hue, so it reads for colour-blind players. The look settings have no soil material: the mesh's own slot is the material. The artist makes the material and sets the slot, and the art reviewer checks it; a soil material from the Interchange importer can't read custom data, so the slot never holds one.
   - **The placeholder soil** lerps from `TilledColor` to `WateredColor` by the same fraction, so the steps show without art too.
   - Watering a tile keeps its soil instance in its set: the meshes component updates its transform and custom data in place (`OnTileChanged`), adding and removing nothing.
- **Instances are named by ID.** For each tile the meshes component keeps which set and which `FPrimitiveInstanceId` its soil and its crop instance have, in an array in the field's tile order. It never stores an instance index.
- **Updates follow the field's events,** and nothing ticks:
   - `OnTileChanged` (a tool use): only that tile. If a part keeps its set, its transform and custom data are updated in place; otherwise the instance is removed from the old set and added to the new one.
   - `OnTilesChanged` (a new day, a restore, a resize): every set is rebuilt in one pass. The sets are cleared, each set's instances are added in one batch (`AddInstancesById`) with their custom data. The component's instance data manager sends only the changed instances to the renderer, so nothing marks render state dirty. It runs under a `TRACE_CPUPROFILER_EVENT_SCOPE` and counts against the new day's 100 ms ([Architecture.md, section 10](../Architecture.md#budget)).
- **The set components:** no collision, no overlap events, no effect on navigation, shadows on, ticking off, mobility Movable (the engine's default for instanced components; a static one may not change its instances during play, and an unmoving movable primitive keeps its cached virtual shadow map pages). They are attached to the meshes component with instances in the grid's space, so moving the grid in the editor moves the field.
- **The look settings live on the meshes component and are set in `BP_FarmGrid`:** the tilled soil mesh, the height crops stand at, the placeholder material, and the placeholder shapes (the engine's cube and cylinder, found with `ConstructorHelpers` as [CodingGuidelines.md, section 12.4](../CodingGuidelines.md#124-assets-and-loading) allows for engine placeholders). Anything left empty falls back to the placeholder. Crop meshes come from each crop's data, loaded with its `Visuals` bundle by the content catalogue ([section 2](02-Content.md)), so drawing never loads an asset. A level places `BP_FarmGrid`, never the C++ `AFarmGrid`, so every map's farm looks the same.
- **A crop's look follows its growth, every night it grew shows, and only a ripe crop looks ripe** ([GameDesign.md, section 6](../GameDesign.md), crops). The crop's data (`UFarmCropData`) owns its look for each growth day; `FarmTileLooks` only asks it (`GetGrowthLook`, a mesh and a scale) and places the answer. A crop has a list of **growth stages** (`GrowthStages`, seedling first), each an `FFarmCropGrowthStage` with the growth day it starts on (`StartDay`) and its mesh, one **ripe mesh** (`RipeMesh`) and a **stage start scale** (`StageStartScale`, 0.8 by default):
   - From `DaysToMature` watered days on (`IsRipeAt`, the same test `FFarmTileState::IsRipe` and harvesting use) the crop shows its ripe mesh at full size, and never before. A `DaysToMature` below 1 counts as always ripe.
   - Before that, day d shows the last stage whose `StartDay` is at most d (`GetGrowthStageIndex`), so stage k spans its `StartDay` to the next stage's `StartDay` minus 1, and the last stage to `DaysToMature - 1`. The start days are the crop's data, chosen per crop so each look lasts as long as it should: the cabbage (10 days) starts its five stages on days 0, 1, 3, 5 and 8, the potato (6 days) on 0, 1 and 3, the turnip (3 days) on 0, 1 and 2 ([GameDesign.md, section 6](../GameDesign.md)). A day before the first `StartDay`, which only invalid data has, shows the first stage.
   - Within a stage the crop scales evenly, as a whole from its origin at the base, from `StageStartScale` on the stage's first day to 1 on its last: a three-day stage shows 0.8, 0.9, 1.0 and a two-day stage 0.8, 1.0. A one-day stage shows at 1, since its mesh already changes every night; so does each crop's planting day, whose seedling is shown at its full size. A night without growth changes nothing, since growth days don't advance.
   - Retuning a crop's `DaysToMature` keeps its start days: the last stage stretches or shrinks. Shortening it to or below a stage's `StartDay` is a validation error, since that stage would never show; the game then skips the stage (the crop ripens first) rather than fail.
   - **The art rule:** each growth stage mesh is at least `1 / StageStartScale` (1.25) times the one before, in spread (the larger of the bounds' X and Y sizes) and in height (the bounds' Z size), so a new stage at its start scale never looks smaller or shorter than the end of the one before; the art aims at 1.28 for a margin. Spread is what the camera mostly sees and what fills the tile; height is checked too because a crop that gets shorter overnight reads as wilting, and crop heights are far below any limit. The first stage's mesh is at least 0.2 m in spread, so a seedling reads from the play camera on the day it is planted, and no look is wider than 0.6 m, so neighbours on 1 m tiles keep a gap. The ripe mesh has no size rule (a potato's foliage dies back), only a look clearly unlike the last stage. Every material on a crop mesh has **Used with Instanced Static Meshes** saved. Crop materials are instances of `M_Crop`, the project's flat-colour crop material (`BaseColor` and `Roughness` parameters), named `MI_Crop_<Crop><Part>`, the turnip's included. Crop meshes are imported, and reimported, through the Interchange manager with a pipeline override that makes no materials, no collision and no lightmap UVs (a plain editor reimport brings back generated material instances and a convex hull); afterwards each has no simple collision and an `MI_Crop_*` instance in every slot.
   - A missing mesh (a stage without one, no growth stages, no ripe mesh, or a mesh not loaded) draws the placeholder cylinder, unscaled: its height already follows the growth fraction (`GrowthDays / DaysToMature` as a float, seedling to ripe height), so it shows every night too, and its colour turns ripe only when the tile is ripe.
   - Validation (`UFarmCropData::IsDataValid`), all errors: a `DaysToMature` below 1; a `StageStartScale` at or below 0 or above 1; no ripe mesh; no growth stages; a stage without a mesh; a first `StartDay` other than 0; start days that don't strictly increase; a `StartDay` at or after `DaysToMature`; the ripe mesh used by a stage.
   - Crop meshes are named after the crop: `SM_Crop_<Name>_Stage<N>` from `Stage0`, and `SM_Crop_<Name>_Ripe` (`SM_Crop_Turnip_Stage0`), with the origin at the centre of the base on the soil surface, in `Content/Vestige/Meshes`.
- **Seeds go in only in their seasons, and a planting too late asks first** ([GameDesign.md, section 6](../GameDesign.md#crops), "Seeds and the end of the season"; the open choices in its section 15 are built on their recommended options). The crop's data owns the rule, as a pure function tested without a world; the plant ability applies it; the farming component remembers the day's warnings; the HUD shows the days to ripen. Lyra has no seasons or confirmations to take from; the reasons follow its failure-tag idea, as every tool reason does ([section 15](15-EffectsAndFeedback.md)).
   - **A crop's seasons** are its `Seasons` tags, read against the calendar (`FVestigeCalendar`, [section 4](04-Time.md)). Only tags that are seasons of the calendar count, matched exactly (`HasTagExact`, never `HasTag`, which matches a listed child tag too); a crop that lists none of them grows in every season, and data validation reports it (below), so a forgotten field is caught in the editor without blocking play and a mod's crop naming a season the calendar lacks still grows. `bool UFarmCropData::GrowsIn(const FGameplayTag& Season, const FVestigeCalendar& Calendar) const` answers for one season; withering ([Roadmap.md, 4.2](../Roadmap.md#42-farming-depth)) asks it on `OnSeasonStarted`.
   - **The fit:** `FFarmSeasonFit UFarmCropData::GetSeasonFit(const FVestigeCalendar& Calendar, int32 Day) const`, for planting on day count `Day`. `FFarmSeasonFit` is a plain struct in `Content/FarmCropData.h`: `EFarmSeasonFit Fit` (`Fits`, `OutOfSeason`, `TooLate`: a fixed set of rule outcomes, so an enum), `int32 DaysToRipe` (the crop's `DaysToMature`), `int32 DaysToDeadline`, and `int32 PlantSeasonIndex` and `DeadlineSeasonIndex`, indices into the calendar's seasons, `INDEX_NONE` when there is none. Out of season when the date's season isn't one the crop grows in; `PlantSeasonIndex` is then the first season after it, in the calendar's order and on into the next year, that the crop grows in. Otherwise `DaysToDeadline` is the date's `DaysLeft` plus `GetDaysPerSeason()` for each following season in a row that the crop grows in, `DeadlineSeasonIndex` is the first following season it doesn't, and the planting is too late when `DaysToRipe > DaysToDeadline`. A crop that grows in every season of the calendar, and every crop when the calendar has no seasons, has no deadline (`DaysToDeadline` is `MAX_int32`, `DeadlineSeasonIndex` is `INDEX_NONE`) and always fits. The count assumes a watering every night (GameDesign.md says so). The loop runs over the calendar's seasons at most once; nothing is cached.
   - **Its report values:** `FFormatNamedArguments FFarmSeasonFit::GetReportValues(const FVestigeCalendar& Calendar, int32 Day) const` gives the calendar's `GetReportValues(Day)` (`Day`, `Season`, `SeasonInSentence`, `DayOfSeason`, `DaysLeft`), `DaysToRipe`, and for out of season `PlantSeason` and `PlantSeasonInSentence`, for too late `DaysToDeadline`, `DeadlineSeason` and `DeadlineSeasonInSentence` (each season's `DisplayName` and `NameInSentence`). No value is a finished phrase.
   - **The plant ability** (`UFarmGameplayAbility_Plant::CanUseOn`) reports the first of these that applies, once per press: no crop for the seed in hand, `Farm.NothingToPlant`; out of season, `Farm.OutOfSeason`; no tile state, `Tool.NoTarget`; a tile that can't take seeds, `Farm.CantPlant`; too late and not yet warned today, `Farm.TooLate`, or its child `Farm.TooLate.LastDay` when `DaysToDeadline` is 0 ([section 15](15-EffectsAndFeedback.md)). It reads today from the clock (`UVestigeClockSubsystem::Get(GetWorld())`: `GetCurrentDay` and `GetCalendar`); without a clock (an editor world) every crop fits. It builds the report's values only when the base asks for a reason (the press); a repeat computes the fit, a few integer steps, and stays quiet. With no target tile at all the base reports `Tool.NoTarget` before it asks `CanUseOn`, so off the field "Stand facing a farm tile." comes first, as it does for `Farm.NothingToPlant`.
   - **Warned once per crop per day** (option (b)): the press refused with `Farm.TooLate` (either form) plants nothing and uses no seed; a later press that day plants that crop as usual and says nothing. The base calls `OnPressRefused` just before it reports a press's reason ([section 9](09-AbilitySystem.md)); the plant ability's override, for a reason that `MatchesTag(Farm.TooLate)`, calls `UFarmingComponent::RememberWarning(Feedback_Farm_TooLate, CropId, Day)` and sets its `bWarnedThisPress`. `CanUseOn` lets a too-late crop through only when `WasWarned(Feedback_Farm_TooLate, CropId, Day)` and not `bWarnedThisPress`, so the rest of a held press after the warning plants nothing: the player hasn't read it yet. `EndAbility` clears `bWarnedThisPress`. A crop's ID is its primary asset ID (`FarmCrop:Base.Cabbage`), so the warning is per crop.
   - **The memory is the farming component's,** not the ability's, because the ability is granted again on every tool switch and the player waters between plantings. `UFarmingComponent` keeps `int32 WarningsDay = INDEX_NONE` and `TSet<TPair<FGameplayTag, FPrimaryAssetId>> Warnings`; `RememberWarning(const FGameplayTag& Warning, const FPrimaryAssetId& Subject, int32 Day)` empties the set first when `Day` isn't `WarningsDay`, and `WasWarned(...)` is false for any other day. So a new day, a developer jump (`SetDay`, which broadcasts nothing) and a new pawn (a load, another map) forget it, with no event to listen to and nothing to clean up. Not saved: a load warns again once. The store knows no rule and no tool: the reason tag and a content ID are its key, and the abilities decide what they mean.
   - **Option (a) instead** (plant and warn once per press, [GameDesign.md, section 15](../GameDesign.md#15-open-questions)): drop the too-late step from `CanUseOn`, `OnPressRefused`'s override, the memory, and "Press again to plant anyway." from the two texts, and report `Farm.TooLate` after the press's first use through a base hook for that, which doesn't exist yet. The rule, the values and the tags stay.
   - **Validation** (`UFarmCropData::IsDataValid`, errors): an empty `Seasons` ("the crop grows in every season; list every season for that"), and each tag the game data's calendar (`UVestigeGameData::Get().GetCalendar()`, `FindSeason`) doesn't have. The second check is skipped when that calendar has no seasons: the game data didn't load, and the asset manager's error already says so. Every base crop (`DA_Crop_Turnip`, `_Potato`, `_Cabbage`) lists `Vestige.Season.Spring`, set by editor script: `get_editor_property` returns a copy of the tag container, so the script fills the copy with `import_text` (checking its result), writes it back with `set_editor_property`, saves the asset, and logs `export_text()` after a reload.
   - **The days to ripen on the HUD** are `DaysToMature`, which doesn't change with the date, so the label is rebuilt on the hand's event only ([section 6](06-UserInterface.md)). `static const UFarmCropData* UFarmSeedFragment::FindCropOf(const UVestigeItemData* Item, const UVestigeContentCatalog* Catalog)` (the crop the item's seed fragment names, or `nullptr`) is the one way from an item to its crop, used by the plant ability and the HUD.
   - **Cost:** per try, a tile lookup as before, the date (integer steps) and one set lookup; per press that is refused, one set of report values. Nothing per frame, per hour or on the new day.
- **Each tile holds a water level** in whole steps, raised by watering and lowered each night, and a crop grows on a night its tile has any ([GameDesign.md, section 15](../GameDesign.md#15-open-questions), water on each tile and what a crop needs; built on the recommended options until @DunderGG answers). Lyra has nothing like it; Epic's developer settings page (`UDeveloperSettings`) is the reference for where the numbers live.
   - **The data.** `FFarmTileState` has `int32 WaterLevel` (0 is dry), with `GetWaterLevel()` and `IsWatered()` (`WaterLevel > 0`). Grass always has 0. The numbers are `FFarmWaterRules`, a `USTRUCT` in `Farming/FarmTileState.h`: `MaxLevel` (2, the cap), `StepsPerWatering` (1, what one use of the can adds) and `NightlyFall` (1). `UFarmFieldSettings` (developer settings, `Farming/`, `Config = Game, DefaultConfig`, Project Settings > Game > Vestige Farm Fields) holds one, and `UFarmFieldSettings::Get().GetWaterRules()` returns it with each number at least 1, as the clock's settings clamp theirs. `UFarmFieldSubsystem` passes it to `UFarmField::Initialize(FName InFieldId, const FIntPoint& InSize, const FFarmWaterRules& InWaterRules)` when it makes a field, and the field keeps its copy (`GetWaterRules()`) through a resize. The tile's functions take the numbers as parameters, so the rules are tested with any cap and no world or settings. A changed setting reaches the next game session, not fields already made.
   - **Watering.** `bool FFarmTileState::AddWater(int32 Steps, int32 MaxLevel)` raises the level by `Steps`, to at most `MaxLevel`; it returns false, changing nothing, on grass, for `Steps` below 1, and at the cap. `CanAddWater(int32 MaxLevel)` says whether it would. Empty tilled soil and ripe crops take water; tilling starts dry; planting and harvesting keep the level. `UFarmField::Water(const FIntPoint&)` is the can's action, `AddWater(StepsPerWatering, MaxLevel)`, broadcasting `OnTileChanged` when it changed the tile. Every later source goes through `AddWater` with its own steps.
   - **The watering can** (`UFarmGameplayAbility_Water::CanUseOn`) reports the first of these that applies: no tile, `Tool.NoTarget`; grass, `Farm.CantWater` ("Nothing to water here."); at the cap, `Farm.Soaked` ("The soil is already soaked.", [section 15](15-EffectsAndFeedback.md)); a tile this press has already watered, `Farm.Soaked` too, which only a repeat reaches and a repeat reports nothing. A refusal costs no stamina (the base's rule) and, once the can holds water, no water. **A held press waters each tile once:** the ability keeps `TSet<FIntPoint> TilesWateredThisPress`, adds the tile in `UseOn` when the field changed, and empties it in its `EndAbility` override before calling the base, so every press starts empty; a second step takes a new press. Without it the base's repeat would water the faced tile again after each use, emptying the can on one tile. The rule is the can's, not the base's: tilling, planting and harvesting change a tile once by their own rules, and a later tool may want repeats.
   - **The night, in order** (`UFarmField::AdvanceDay`, then `FFarmTileState::AdvanceDay(int32 NightlyFall)` on each tile): first growth, a planted crop that isn't ripe grows one growth day if the tile has water; then the fall, every tile's level drops by `NightlyFall`, not below 0, planted or not. So a tile watered twice today grows tonight and tomorrow night, and growth never needs more than one step. The field broadcasts `OnTilesChanged` once, after every tile. Later items slot in without a redesign: contamination's effect on growth joins the growth step (the crop's tolerance and the tile's contamination); dawn sources run after every field's night, the sprinkler adding its steps and rain filling to the cap. Those need an event from `UFarmFieldSubsystem` after `AdvanceFields` (a listener of the clock's `OnNewDay` has no order against the fields) and a field function that waters many tiles with one `OnTilesChanged`; both come with the sprinkler, not now. Dirty water is `AddWater` plus contamination on the same tile.
   - **A crop needs any water.** `UFarmCropData::WaterNeed` is removed (unread, [CodeReview.md, L2](../CodeReview.md#low)): every crop grows on a night its tile has a step. Thirstier crops come back as data with a drier season. A dry crop doesn't grow and loses nothing; how it looks thirsty is a follow-up item.
   - **Saving.** `FFarmTileSaveData` holds `int32 WaterLevel`; `FFarmFieldsSaveData::Version` is 1, since a missing level defaults to dry, a valid state ([section 1](01-Saving.md)): a record without it loads every tile dry, with crops, growth and soil kept. `FFarmTileState::Restore(EFarmTileState SavedState, int32 SavedWaterLevel, int32 SavedGrowthDays, const UFarmCropData* SavedCrop, int32 MaxLevel)` clamps the level to 0 to `MaxLevel` (0 on grass), so a lowered cap never leaves a tile above it.
   - **Cost and logging.** Watering writes one tile and one instance's custom data in place. The night adds two integer steps per tile to the loop under `UFarmField::AdvanceDay`'s trace scope, and the redraw one float per instance. Nothing per frame or per hour. No new log lines: refusals reach the log through the feedback subsystem, and a clamped restore is silent, as growth's is.
- **Gameplay never calls the meshes component.** The field's events reach it directly. Targeting, the target highlight and anything else that needs a tile's place ask the grid for coordinates or a transform.
- **Extension points name tiles by coordinates.** `On Crop Harvested` and `On Tool Used` carry the tile's coordinates (an `FIntPoint`) ([Architecture.md, section 12](../Architecture.md#extension-points-today)).
- **One set of components per field.** Splitting a large field into chunks (for example 32 by 32 tiles each, so culling and rebuilds work on smaller pieces) waits for a profile of a farm-sized field that shows the need.
- **Tiles have no collision.** The farmer walks on the level's floor. If placing objects needs to know what is on a tile, the grid answers by coordinates, not with a shape per tile.

**Tests** (`Source/Vestige/Tests/`):

- `Vestige.FarmCrop.*`: which stage and scale each growth day shows for the start days given, uneven spans included, the ripe mesh at full size only from `DaysToMature` on, missing meshes giving none, the validation rules, and every base crop showing a mesh for each of its days, its ripe mesh only when ripe, a readable seedling, no look wider than its share of the tile, stage meshes that keep the art rule and materials with the instanced usage saved. The season fit on made-up calendars and crops (fits on the last day it can ripen, too late a day after; out of season and the next season to plant, into the next year; a following listed season adds its days; a crop of every season, of no season and of unknown seasons; a calendar without seasons; no days left on the last day; the report values) and its validation rules.
- `Vestige.Farming.*` for planting in and out of season: refused out of season with nothing planted and no seed used, the season before the tile, the first late press warning and planting nothing (seed count, stamina and `On Tool Used` unchanged), the next press planting quietly, a held press after the warning planting nothing (the same three unchanged), the warning per crop, kept across a tool switch and forgotten on another day, the last day's form, a tile reason before the warning and leaving it unasked. `Vestige.Farming.OnlyThePressRefusalIsToldToTheAbility` covers the base's `OnPressRefused` with the test tool ability (once on a refused press, not again on a refused repeat, never off the field).
- `Vestige.FarmTileLooks.*`: the look of each state with art and with placeholders (grass, tilled, each growth stage, ripe), without a world; the soil's and the crop's water value at 0, 1 and 2 of a cap of 2 (0, 0.5, 1) and of another cap; the soil in one set whatever its water; the placeholder soil darker with each step.
- `Vestige.FarmFieldMeshes.*`: a grid with a field of N tiles draws N soil instances and spawns no actor for them; tilling, planting and harvesting move or add or remove exactly one instance; watering keeps the soil instance in its set and changes only its custom data 3; a new day that grows a crop moves it to its next stage's set; a resize redraws every tile; no `UMaterialInstanceDynamic` is created; `M_FarmPlaceholder` has the instanced usage flag; every material on `BP_FarmGrid`'s tilled soil mesh has it too, derives from `M_FarmSoil`, and (editor data) reads custom data index `WaterCustomDataIndex`.
- `Vestige.FarmTileState.*` for water: a watering adds its steps up to the cap and refuses at it, changing nothing; grass takes none; empty soil and a ripe crop take it; tilling starts dry; planting and harvesting keep the level; a night grows a wet crop, then the level falls, on empty soil too, never below 0; a crop watered twice grows two nights and not a third; a dry crop doesn't grow; a restore clamps the level to the cap and to 0, and to 0 on grass.
- `Vestige.FarmField.*` for water: the field's own rules (a cap of 3, two steps per watering) decide its watering and night; a resize keeps them; fields the subsystem makes get `UFarmFieldSettings`' rules; the settings' getter lifts numbers below 1 to 1; the save round trip keeps each level; a saved tile without a `WaterLevel` restores dry with its crop and growth.
- `Vestige.Farming.*` for watering: a soaked tile is refused with `Farm.Soaked` (stamina and `On Tool Used` unchanged), grass with `Farm.CantWater`; a held press on one tile through several use times raises it one step, then waters the next tile it faces, and a return to the first changes nothing; a new press adds the second step.
- The rule tests cover `FFarmTileState` and `UFarmField`; the farming, targeting and cheat tests name tiles by coordinates.

**Pitfalls:**

- Storing instance indices. Removing an instance moves others (or swaps the last into its place), so a stored index soon points at another tile's instance. Use the IDs.
- Calling `SetStaticMesh` on a set's component to change a tile's look. That changes every tile in the set; move the instance to another set.
- A material without **Used with Instanced Static Meshes**: grey tiles in play, and a "missing usage flag" line in the log.
- Custom data written before `NumCustomDataFloats` is set is dropped without a warning.
- Marking render state dirty or updating navigation per instance inside a loop over the field.
- The hierarchical instanced component for Nanite art: it costs CPU time for culling the GPU already does.
- A dynamic material per tile "just for the placeholder": the placeholder is what the field looks like until there is art, so it has to scale too.
- Indexing a crop's stages by growth day, or falling back to the last mesh: a long crop then needs a mesh per day, or shows its ripe look days early. Ask the crop for its look.
- Scaling a crop mesh whose origin isn't at its base: it then sinks into the soil or floats as it grows.
- Putting the ripe mesh in `GrowthStages` as the last stage: it then shows before the crop is ripe. Validation reports it.
- Matching a season with `HasTag` or `MatchesTag`. `HasTag` also matches through the parents of the crop's tags, so a crop listing a child of a season (a mod's `Vestige.Season.Spring.Late`) would grow in spring, and `MatchesTag` on the calendar's tag matches a crop listing the parent. Seasons match exactly (`HasTagExact`), in `GrowsIn` and in the check for a crop that lists none of the calendar's seasons.
- Remembering a warning on the tool ability: the ability is granted again on each tool switch, so it would warn again after the watering can. Remember it on the farming component, by day number.
- Letting the warning's own press plant on a repeat: the warning would scroll by under a held key while seeds go in. A warning confirms from the next press on.
- Two silent refusals in a held press, since only the press reports: a press that starts on a tile that can't take seeds and reaches one where the planting is too late, and a switch to other seeds during a held press (every seed item names `DA_Tool_Seeds`, so the same plant ability stays active) to a crop that is too late. Either plants nothing and says nothing more; releasing and pressing again warns. If play-testing finds it confusing, the fix is a base rule that lets a repeat report a reason the press didn't, for every tool, made a roadmap item first.
- Letting the fall run before growth: a crop watered once would never grow. Growth reads the level first.
- Writing the water level, not the fraction, to custom data: the soil material would then hard-code the cap.
- Raising the save version for a field whose default is a valid state: before the first public build an older record is dropped whole ([section 1](01-Saving.md)), so the version is raised only for a change that would load wrong.
- Reading `UFarmFieldSettings` inside `FFarmTileState`: the rules would then need the settings to test. The field passes the numbers.
- A crop without `Seasons` in a saved asset: it grows in every season and is never too late. Validation reports it; `Vestige.Content.EveryCropAndItemPassesValidation` fails on it.
