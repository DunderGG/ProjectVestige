# 6. User interface

One of the [system guides](../Systems.md); read [How to use this document](../Systems.md#how-to-use-this-document) first.

**Status:** the HUD is built in UMG ([CodeReview.md, H7](../CodeReview.md#h7--the-hud-is-raw-slate-written-in-c), 2026-11-08, approved by a senior Unreal C++ reviewer agent after two rounds, whose approval counts as David's): `AVestigeHUD` builds the texts and pushes them to `WBP_Hud` (`UVestigeHudWidget`), with each feedback message in a `WBP_HudMessage` (`UVestigeHudMessageWidget`); `BP_HUD` names the widget and `BP_GameMode` names `BP_HUD`. Menus, the hotbar row and an inventory screen in UMG are milestone 2; Common UI comes with the first menu.

**References:** Epic's "UMG UI Designer", "Common UI" and "UMG Viewmodel" (MVVM plugin) pages; Lyra's UI: `UGameUIManagerSubsystem` and `UGameUIPolicy` (CommonGame plugin), a `UPrimaryGameLayout` with layers (game, game menu, menu, modal) that widgets are pushed onto, and the UIExtension plugin (`UUIExtensionSubsystem`), which lets features add widgets to named HUD slots without the HUD knowing them. Lyra's `ALyraHUD` hosts no widgets (its comment says it exists for debug drawing; the experience's "Add Widgets" action pushes `ULyraHUDLayout`), and its HUD parts are `UCommonUserWidget` C++ bases with `meta = (BindWidget)` parts and `EditAnywhere` style properties (`ULyraPerfStatWidgetBase`, `ULyraReticleWidgetBase`).

**The UMG HUD (H7).** The HUD is laid out in Widget Blueprints over C++ base classes. The hotbar row is [Roadmap.md, 4.6](../Roadmap.md#46-interface-and-input).

*Take, skip, change from Lyra and Epic's UMG guidance:*

- **Take:** C++ base classes with `BindWidget` parts and style properties the Blueprint sets, so layout, fonts and colours are edited in the UMG designer without a recompile; one root HUD layout widget per player, added with `AddToPlayerScreen` as Lyra's `UGameUIPolicy` does. From Epic's "UMG Best Practices" tech blog: an abstract C++ `UUserWidget` base per widget whose `BlueprintImplementableEvent`s are the contract with the Blueprint, never `BlueprintNativeEvent`; widgets set up again with new data rather than made anew (pooled); no Blueprint `Tick`, no property bindings, and few animations in a HUD. From Epic's "UMG Best Practices" documentation page: event-based updates, every Widget Blueprint authored at 1920x1080 and DPI scale 1.0 under the project's one DPI curve, Auto slot sizing for parts sized by their content, plain brushes rather than materials for UI art, and reusable parts as their own User Widgets.
- **Skip:** CommonGame's UI manager, policy and layered `UPrimaryGameLayout`, Common UI and the UIExtension plugin (the CommonUI plugin is on for Common Input's `UCommonInputSubsystem`, which the key hints follow, [section 5](05-Input.md), gamepad key hints; its widgets, routing and viewport client wait for the first menu). The HUD is one layer with no menus yet; Common UI comes with the first menu (reparenting the bases to `UCommonUserWidget` then is cheap), and named HUD slots with the first feature or mod that adds a HUD element (rules below). Skip the MVVM plugin too: its bindings are authored in the designer's View Bindings panel, the HUD has six fields, and the guide already says viewmodels pay off once screens have many fields. Skip Invalidation and Retainer Boxes: the HUD is about a dozen widgets, and one can be added if a profile asks for it.
- **Change:** our `AHUD` hosts the layout widget, since there is no experience to push it. The blog's Blueprint fills its widgets from a data object when an event fires; ours has the C++ base set its `BindWidget` parts and then fire the event, so the Blueprint needs no graph to work but can restyle from the event (a hybrid: our assets are made by a commandlet, which can build a widget tree but not reliably a graph). The blog's Blueprint also creates the child widgets; ours are made by the C++ base from a widget class the Blueprint names.

*Classes (all in `UI/`):*

- **`AVestigeHUD`** is the data side, as the code review suggests, and the exception to the rule that a widget's C++ base binds to its own events: it follows the clock, the pawn's interaction component, the player state's inventory and ability system and the feedback subsystem (whose reports it turns into messages through `DA_FeedbackResponses`, [section 15](15-EffectsAndFeedback.md)), builds each text when its event fires, and **pushes** it to the widget (`HudWidget->SetBagText(...)`, each push checking `HudWidget`). It is an acceptable data object for six texts; it doesn't grow with new HUD parts (see the hotbar boundary below). The widget never reads the HUD, so no per-frame bindings remain.
   - `UPROPERTY(EditDefaultsOnly, Category = "HUD") TSubclassOf<UVestigeHudWidget> HudWidgetClass`. At `BeginPlay`, only when `PlayerOwner` has a local player and the world has a game viewport (the guard: `CreateWidget` on a controller without a player logs a PIE error and returns null), it creates the widget (`CreateWidget<UVestigeHudWidget>(PlayerOwner, HudWidgetClass)`, held in a `UPROPERTY() TObjectPtr`), adds it with `AddToPlayerScreen`, and only then starts following, so each first refresh reaches the widget. Without a widget class it logs an error (`LogVestige`), follows nothing and turns its tick off.
   - At `EndPlay` it unbinds, calls `RemoveFromParent` and clears `HudWidget` (the widget's outer is the game instance, which outlives the map). A map change with `open` destroys the HUD and makes a new one. Seamless travel would carry the HUD over (`GetSeamlessTravelActorList` adds it), so this needs revisiting if the game ever uses it.
   - The clock is the one value the HUD reads without an event: the HUD's `Tick` (an `AHUD` ticks by default, `HUD.cpp`), with the comment [CodingGuidelines.md, section 12.1](../CodingGuidelines.md#121-ticking) asks for, compares the clock's day and shown minute with the ones last pushed and calls `RefreshStatusText` only when one changed. The clock's `OnMinuteStarted` can replace the tick when the clock shows every minute ([Roadmap.md, 4.6](../Roadmap.md#46-interface-and-input)). The item in hand's event calls `RefreshStatusText` directly. The tick is turned off (`SetActorTickEnabled(false)`) when there is no widget or no clock.
   - The status line is "{Date}   {Clock}   |   {Item}". The date part is today's date from the clock's `GetDate` with its season's `DisplayName` from the calendar ([section 4](04-Time.md), the calendar), built by the public static `FormatDate(const FVestigeDate&, const FText& SeasonName)` only when the day changes and kept in `DateText`, so the line's ten-minute rebuild doesn't format it again: "Spring 3, 25 days left" (`{Season} {DayOfSeason}, {DaysLeft} {DaysLeft}|plural(one=day,other=days) left`), "Spring 27, 1 day left", "Spring 28, last day" (`{Season} {DayOfSeason}, last day`), and "Day 31" (`Day {Day}`, the day count) when the date has no season name. The argument names mean what they mean in the feedback reports: `Day` is the day count, `DayOfSeason` the day in the season. The last day is a text of its own: `FText`'s plural keywords are CLDR's (`zero`, `one`, `two`, `few`, `many`, `other`, checked in 5.8's `TextFormatArgumentModifier.cpp`), and English puts 0 in `other`.
   - The messages model (`FVestigeHudMessages`) has one expiry timer, and its cap and times come from `UVestigeHudSettings`; when the list changes the HUD pushes the whole list (`ShowMessages(Messages.GetMessages(), MessageSeconds)`).
- **`UVestigeHudWidget : UUserWidget`** (`Abstract`, `meta = (DisableNativeTick)`, which `UUserWidget` declares on itself and doesn't inherit, so it is set here), the base of `WBP_Hud`.
   - Parts (`BindWidget`): `UTextBlock` `StatusText`, `StaminaText`, `BagText`, `PromptText`, `KeyHintsText`; `UWidget` `PromptBox` (the backdrop around the prompt, collapsed while the prompt is empty); `UVerticalBox` `MessageList` (concrete, since the C++ sets its slots).
   - Style (`EditDefaultsOnly`, category **Style**): `StaminaColor` (white), `StaminaWarningColor` (red), `MessageSpacing` (6, the gap above every message box but the first), `TSubclassOf<UVestigeHudMessageWidget> MessageWidgetClass`.
   - Functions (C++): `SetStatusText`, `SetStamina(Text, Stamina, MaxStamina, bOutOfStamina, bExhausted)`, `SetBagText`, `SetPromptText`, `SetKeyHintsText`, `ShowMessages(const TArray<FVestigeHudMessage>&, double Lifetime)`. Each sets its parts first, then fires its event.
   - Events (`BlueprintImplementableEvent`, category **HUD**), for restyling without C++; an event nobody implements costs nothing: `OnStaminaChanged(int32 Stamina, int32 MaxStamina, bool bOutOfStamina, bool bExhausted)` (a stamina bar could be drawn from the numbers), `OnPromptChanged(bool bShown)`. The HUD passes the numbers it already reads for the stamina text.
   - The constructor sets the widget's default visibility to `HitTestInvisible` (with the protected `SetVisibilityInternal`, as `UUserWidget`'s own constructor does, so no visibility event fires on the class default object), so the HUD never takes the mouse and stays out of the hit-test grid. In the constructor rather than `NativeOnInitialized`, which doesn't run for a widget made without a player unless the Blueprint's `bCanCallInitializedWithoutPlayerContext` is set.
   - `ShowMessages` shows message *i* in box *i*, oldest first, and collapses the boxes beyond the list. Boxes are made from `MessageWidgetClass` and added to `MessageList` (Auto height, centred, `MessageSpacing` above all but the first) only when the list is longer than the boxes made so far, and are never removed: at most `MaxMessages` boxes for the session, made once. No local is named `Slot`, which would shadow `UWidget::Slot`.
- **`UVestigeHudMessageWidget : UUserWidget`** (`Abstract`), the base of `WBP_HudMessage`, one feedback message in its own box. Part: `UTextBlock` `MessageText`. `ShowMessage(Text, StartTime, Lifetime)` sets the text, keeps the times, sets the starting opacity, shows the box and fires `OnMessageShown` (`BlueprintImplementableEvent`); `Hide` collapses it. `NativeTick` calls the public `UpdateOpacity(Now)`, which sets the whole widget's render opacity to `FVestigeHudMessages::GetOpacity(StartTime, Now, Lifetime)` (now from `GetWorld()`, checked), so the backdrop and the text fade together.
   - Why a tick and not a UMG animation: Slate ticks only what it paints, so a collapsed box costs nothing and at most five boxes tick while their messages show; `SetRenderOpacity` invalidates paint only when the value changes. A running animation also keeps the widget ticking, adds sequence evaluation and would need its length scaled to the configurable `MessageSeconds`, and the blog asks for few animations in a HUD.
- **The hotbar boundary (4.6, so the HUD doesn't grow).** The hotbar row will be its own widget base that finds the inventory component once (`GetOwningPlayerState()`) and binds to `OnInventoryChanged` itself, as Lyra's HUD parts find their own data (but without Lyra's `NativeTick` polling in `ULyraWeaponUserInterface`). Its slot widget gets `SetupSlot(const FVestigeInventorySlot&, bool bSelected)` and an `OnSlotSet` event, one pooled widget per slot, like the blog's `SetupOffer` and `OnOfferSet`. `AVestigeHUD` gains nothing for it.

*Assets:*

- `Content/Vestige/UI/WBP_Hud` (parent `UVestigeHudWidget`), authored at 1920x1080 and DPI scale 1.0: an overlay root, so every part is placed by its slot's alignment and padding, sized by its content (Auto): the status panel top left, 24 from the edges (a border, black at 45 %, padding 16 by 10, with the status line in Roboto Bold 20, then stamina and bag in Roboto Regular 16, 4 apart); the prompt box centred, 160 below the middle (padding 16 by 8, Bold 18), collapsed; the message list centred at the bottom, 80 up; the key hints centred at the bottom, 24 up (Regular 13, light grey). Every text has a black shadow offset by 1, 1 (a UMG text's shadow is transparent by default). Fonts are the engine's `/Engine/EngineFonts/Roboto`. The texts' preview strings are culture-invariant, so they aren't gathered for translation. `MessageWidgetClass` is `WBP_HudMessage`.
- `Content/Vestige/UI/WBP_HudMessage` (parent `UVestigeHudMessageWidget`): a border (black at 45 %, padding 16 by 8) around `MessageText` (Bold 18, warm yellow).
- `Content/Vestige/Blueprints/BP_HUD` (parent `AVestigeHUD`) with **HUD Widget Class** `WBP_Hud`; `BP_GameMode`'s **HUD Class** is `BP_HUD`. `AVestigeGameMode` keeps the native `AVestigeHUD` as its C++ fallback. The references are hard ([Architecture.md, section 8](../Architecture.md#8-c-and-blueprints)): the widgets are small and needed the moment play starts, so nothing loads during play, where a soft class in settings would only add a load at the start of play.
- **Making widget assets with a headless commandlet** (how `WBP_Hud` and `WBP_HudMessage` were made; the designer edits them like any widget). The commandlet:
   - creates each widget with `FWidgetBlueprintOperationUtils::CreateWidgetBlueprint` (which copies the project's `bCanCallInitializedWithoutPlayerContext` and sets up the tree), not a bare `FKismetEditorUtilities::CreateBlueprint`;
   - builds the tree with `WidgetTree->ConstructWidget<T>(Class, Name)`, sets `bIsVariable` on the parts and calls `OnVariableAdded(Name)` for every widget, since the compiler ensures each widget has a GUID;
   - sets every slot's alignment, padding and size rule, every text's font, colour and shadow colour, and every border's brush colour and padding;
   - compiles with `FKismetEditorUtilities::CompileBlueprint` and fails unless the status is up to date (a missing `BindWidget` part is a compile error);
   - sets the class defaults (`MessageWidgetClass`, `HudWidgetClass`, `BP_GameMode`'s `HUDClass`), then registers the new assets with the asset registry and saves the packages.

*Module:* `UMG` is a private dependency; `Slate` and `SlateCore` stay (UMG needs them, and `FSlateColor` is in the widget header). Test-only getters: `AVestigeHUD::GetHudWidgetClass` and `UVestigeHudWidget::GetMessageWidgetClass`.

*Tests* (`Vestige.UI.*`, with widgets created by `CreateWidget` on the test world, which needs no viewport and binds the `BindWidget` parts): three guard the assets (`TheGameModeShowsTheHudWidget`: `BP_GameMode`'s HUD class has a widget class whose message widget class is set; `OnlyTheMessageBoxesTick`; `TheHudDoesNotTakeTheMouse`), and the rest cover the message boxes and their fade, the prompt box, the stamina warning colour and the date text (`TheDateShowsTheSeasonAndTheDaysLeft`, `TheDateWithoutASeasonShowsTheDayCount`, through `FormatDate`, since the status line itself needs a local player). `Vestige.HudMessages.*` and `Vestige.HudSettings.*` test the messages model and its settings. A `BP_HUD` without a widget class is checked by hand, since the test spawner has no local player.

**Rules:**

- **Presentation only.** Widgets read state and listen to events; they never change game state except by calling the owner's public functions in response to player input ([Architecture.md, section 7](../Architecture.md#7-presentation-ui-audio-and-effects)).
- **UMG Widget Blueprints with C++ base classes** for the HUD, menus and the inventory: the abstract C++ base holds the logic and binds to events (the HUD's texts are the exception: `AVestigeHUD` pushes them), sets the parts it needs (`meta = (BindWidget)`), and fires `BlueprintImplementableEvent`s after it has, so a Blueprint can restyle without C++; never `BlueprintNativeEvent`. The Blueprint holds layout and style. Widgets showing a thing get a setup function (`SetupSlot`) and are set up again rather than made anew.
- **Authoring.** Every Widget Blueprint at 1920x1080 and DPI scale 1.0 under the project's one DPI curve; overlay and box panels with Auto sizing where they copy a simple layout; plain brushes rather than materials for UI art; Collapsed rather than Hidden for parts not shown; `HitTestInvisible` for everything that takes no input. No Blueprint `Tick`, no property bindings, and few animations in the HUD.
- **Event-driven updates.** Widgets update when an event fires, not through UMG property bindings, which run every frame ([CodingGuidelines.md, section 12.6](../CodingGuidelines.md#126-user-interface)). The MVVM plugin's viewmodels are a good fit once screens have many fields.
- **Layers.** Once there is more than one menu, adopt Lyra's layer idea: one root layout with named layers, and screens pushed and popped on a layer stack. Common UI provides this plus gamepad navigation and input routing; adopt it when gamepad menus are needed, and log the decision.
- **HUD extension points.** For mods and for features that add HUD elements (stamina, weather), use named slots the way Lyra's UIExtension does, rather than editing the HUD for each feature.
- All text is `FText` ([section 18](18-Localization.md)); 24-hour clock everywhere.

**Pitfalls:**

- Widgets that cast to the character or search the world to find their data. Give them their data when they're created, or let them find it once.
- Creating and destroying widgets often (inventory slots on every refresh). Create once, update contents.
